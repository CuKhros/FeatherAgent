# FeatherAgent v1.2.1-rc.1 Changes

Date: 2026-11-24

`v1.2.1-rc.1` closes the R1 gate issue from the v1.2.0-rc.1 Windows retest, adds the `review-gate` three-role loop plugin, and broadens local-model compatibility. It is still a release candidate.

## 1. R1: split warm boot and cold spawn

### Root cause

- Every in-process boot sample used a **new install root**, so Windows re-registered every built-in plugin and antivirus scanned the copied binaries on each sample. The 130–175 ms spikes were cold-cache/AV outliers, not steady-state kernel cost.
- The gate used only 3 samples and reported the median, so one outlier could move the result.
- The reported `spawn_to_socket_ms_min` (166.87 ms on real Windows) measured a different path than `boot_ms_p50`, but both were described as "cold start".

### New measurement contract

`bench --json` now reports two explicit metrics:

| Metric | Meaning | Gate |
|---|---|---|
| `boot_ms_p50` | Warm, in-process boot to socket, **same install root**, 1 warm-up discarded + **5 samples**; median | Windows `<100 ms`, Linux `<20 ms` |
| `cold_spawn_ms_p50` | Real `serve` child process → socket, 3 samples; median | Windows `<250 ms`, Linux `<100 ms` |

`boot_samples_ms` and `boot_warmup_discarded_ms` are included for auditability. `spawn_to_socket_ms_min` remains for backward compatibility but is now an alias of `cold_spawn_ms_min`. Gate keys are `boot_lt_100ms` / `boot_lt_20ms` and `cold_spawn_lt_250ms` / `cold_spawn_lt_100ms`.

Windows cold spawn includes process creation, DLL loading, plugin registration, and real-time protection; 250 ms is a cold-path budget. The 100 ms line applies only to the warm, repeat-launch path that users actually hit after the first install.

### Linux release evidence (3 consecutive runs)

| Run | `boot_ms_p50` | warm-up | `cold_spawn_ms_p50` | warm gate | cold gate |
|---|---:|---:|---:|---|---|
| 1 | 1.228 ms | 1.930 ms | 5.575 ms | pass | pass |
| 2 | 1.246 ms | 1.997 ms | 4.437 ms | pass | pass |
| 3 | 1.259 ms | 2.187 ms | 4.234 ms | pass | pass |

Release binary: 2,406,664 B (2.295 MiB), idle RSS 3,456 KiB, all gates pass. Windows must still be retested on real hardware; Wine numbers are not Windows conclusions.

## 2. `review-gate`: guide → exec → judge

New plugin: `plugins/review-gate`, category `loop`, capabilities `loop.review-gate`, `review.guide`, `review.judge`.

- **guide** receives only the user input plus an environment summary and returns a concrete 3–6 item rubric. It does not answer the task.
- **exec** is the normal kernel turn and never sees the rubric. Tools and project context still use the regular loop.
- **judge** receives the rubric and the final answer, and must return one item per rubric id with non-empty evidence. Empty evidence, a missing item, or a top-level `pass=false` fails the answer.
- Failure emits `review.feedback` with the failed item ids and evidence, raises exec temperature by 0.15 (capped at 1.5), and reruns exec. `max_rounds` is 1–5; when exhausted, the last answer is returned with `status=unapproved` in `review.finished` and `chat.finished.review`.
- Prompt/parse are plugin methods: `review.guide`, `review.judge`, `review.parse_rubric`, `review.parse_verdict`, `review.hardcheck`. The kernel only orchestrates the three independent model calls.
- Temperature bounds: guide 0.2–0.5, exec 0.6–1.5, judge 0.0–0.2. Empty role model means "follow the current global model".
- Events: `review.guide`, `review.verdict`, `review.feedback`, `review.finished`; `chat.finished.review` carries `approved`, `rounds`, `degraded`.
- Default is off. Enable it in WebUI Settings → 三段校验 review-gate, or via config JSON (`review_gate.enabled`).

If guide or judge fails technically, `review.finished.status=degraded` is emitted and the kernel returns the last answer instead of blocking the turn.

## 3. Local model providers

New provider plugins, all OpenAI-compatible and sharing the existing provider contract:

| Plugin | Default base | Endpoints |
|---|---|---|
| `provider-llamacpp` | `http://127.0.0.1:8080` | `/v1/models`, `/v1/chat/completions`, `/v1/embeddings` |
| `provider-ninfer` | `http://127.0.0.1:8080` | same |
| `provider-lmstudio` | `http://127.0.0.1:1234` | same |
| `provider-vllm` | `http://127.0.0.1:8000` | same |
| `provider-openai` | `http://127.0.0.1:8080` | generic OpenAI-compatible local service |

`provider-ollama` keeps native `/api/chat`, `/api/embed`, `/api/tags`, `/api/generate` (FIM), and also accepts a base URL ending in `/v1` for its OpenAI-compatible endpoint.

### API Key

`Config.provider_api_key` is optional and shared by all provider plugins. TUI Settings has an `API Key (Bearer)` field; WebUI has an `API Key（可选）` password field. It is sent only to the selected provider as `Authorization: Bearer <key>`; empty means no header. It is stored locally in `config.json` and is never written to event logs. Tests assert the header on both OpenAI-compatible and Ollama native chat requests.

# FeatherAgent v1.2.1-rc.1 变更说明

日期：2026-11-24

`v1.2.1-rc.1` 关闭 v1.2.0-rc.1 真机复测遗留的 R1 门禁问题，加入 `review-gate` 三角色循环插件，并扩展本地模型兼容层。仍是发布候选版。

## 1. R1：拆分热启动与冷启动

### 根因

- 原先每次进程内 boot 都使用**新的安装根**，Windows 会重新登记全部内置插件，杀毒软件也重复扫描复制出的二进制；130–175 ms 是冷缓存/实时防护尖峰，不是内核稳态成本。
- 门禁只有 3 个样本并取中位，单次尖峰就能左右结果。
- 真机报告里的 `spawn_to_socket_ms_min`（166.87 ms）与 `boot_ms_p50` 测的是两条路径，却都被称为“冷启动”。

### 新测量口径

`bench --json` 现在明确输出两个指标：

| 指标 | 含义 | 门禁 |
|---|---|---|
| `boot_ms_p50` | **热启动**：同一安装根、进程内启动到 socket；先预热 1 次丢弃，再测 **5 次**取中位 | Windows `<100 ms`，Linux `<20 ms` |
| `cold_spawn_ms_p50` | **冷启动**：真实 spawn `serve` 子进程到 socket，3 次取中位 | Windows `<250 ms`，Linux `<100 ms` |

同时输出 `boot_samples_ms` 与 `boot_warmup_discarded_ms`，便于复核。`spawn_to_socket_ms_min` 保留兼容，但已改为 `cold_spawn_ms_min` 的别名。门禁键为 `boot_lt_100ms` / `boot_lt_20ms` 与 `cold_spawn_lt_250ms` / `cold_spawn_lt_100ms`。

Windows 冷启动包含进程创建、DLL 加载、插件登记与实时防护，250 ms 是冷路径预算；100 ms 只约束用户首次安装后的重复启动热路径。

### Linux Release 连续 3 次证据

| 次数 | `boot_ms_p50` | 预热丢弃 | `cold_spawn_ms_p50` | 热启动门禁 | 冷启动门禁 |
|---|---:|---:|---:|---|---|
| 1 | 1.228 ms | 1.930 ms | 5.575 ms | 通过 | 通过 |
| 2 | 1.246 ms | 1.997 ms | 4.437 ms | 通过 | 通过 |
| 3 | 1.259 ms | 2.187 ms | 4.234 ms | 通过 | 通过 |

Release 二进制 2,406,664 B（2.295 MiB），空闲 RSS 3,456 KiB，全门禁通过。Windows 仍需真机复测；Wine 数字不作为 Windows 结论。

## 2. `review-gate`：guide → exec → judge

新插件：`plugins/review-gate`，分类 `loop`，能力 `loop.review-gate`、`review.guide`、`review.judge`。

- **guide** 只拿到用户输入与环境摘要，输出 3–6 条具体验收清单；不回答任务。
- **exec** 走正常内核回合，完全看不到清单；工具与项目上下文仍按原循环执行。
- **judge** 拿到清单与最终答案，必须按每个 id 返回 `pass` 与**非空 evidence**；缺项、空证据或顶层 `pass=false` 均判不通过。
- 失败时发 `review.feedback`，带上失败项与证据，exec 温度 +0.15（上限 1.5）后重答。`max_rounds` 为 1–5；用尽后返回最后一版，并在 `review.finished` 与 `chat.finished.review` 标 `unapproved`。
- prompt 与解析封装为插件方法：`review.guide`、`review.judge`、`review.parse_rubric`、`review.parse_verdict`、`review.hardcheck`；内核只负责三次独立模型调用的编排。
- 温度区间：guide 0.2–0.5、exec 0.6–1.5、judge 0.0–0.2。角色模型留空表示跟随当前全局模型。
- 事件：`review.guide`、`review.verdict`、`review.feedback`、`review.finished`；`chat.finished.review` 带 `approved`、`rounds`、`degraded`。
- 默认关闭。WebUI 设置 →“三段校验 review-gate”可启用，也可直接改配置 JSON 的 `review_gate.enabled`。

guide/judge 技术失败时发 `review.finished.status=degraded`，返回最后一版，不阻塞回合。

## 3. 本地模型 provider

新增 provider 插件，全部走 OpenAI 兼容协议：

| 插件 | 默认 Base | 端点 |
|---|---|---|
| `provider-llamacpp` | `http://127.0.0.1:8080` | `/v1/models`、`/v1/chat/completions`、`/v1/embeddings` |
| `provider-ninfer` | `http://127.0.0.1:8080` | 同上 |
| `provider-lmstudio` | `http://127.0.0.1:1234` | 同上 |
| `provider-vllm` | `http://127.0.0.1:8000` | 同上 |
| `provider-openai` | `http://127.0.0.1:8080` | 通用 OpenAI 兼容本地服务 |

`provider-ollama` 保留原生 `/api/chat`、`/api/embed`、`/api/tags`、`/api/generate`（FIM），也接受以 `/v1` 结尾的 Base 走 OpenAI 兼容端点。

### API Key

`Config.provider_api_key` 可选，所有 provider 共用。TUI 设置新增 `API Key (Bearer)`，WebUI 新增 `API Key（可选）` 密码框。只有当前 provider 的请求会携带 `Authorization: Bearer <key>`；留空则不发送。Key 仅存本机 `config.json`，不写入事件日志。测试同时覆盖 OpenAI 兼容与 Ollama 原生 `/api/chat` 的请求头。

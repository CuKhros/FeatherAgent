# FeatherAgent v1.2.1-rc.4.1 — Changes

Release candidate, 2026-11-25. This patch fixes the four actionable findings from the rc.4 Windows retest (N10–N13) and records the model-size boundary found in N14. It does not replace a stable release.

## N10 — path/file `must_include` is no longer killed by the 12-character limit

rc.4 applied the 12-character phrase limit to every `must_include`. A guide item such as `workspace/notes.txt` (19 characters) was therefore rejected three times and degraded the whole round before the judge could run.

The parser now distinguishes a path/file name from an answer phrase:

- a value containing `/` or `\`, or a dot form with a 1–8 character ASCII alphanumeric extension, is path-like;
- path-like values use a 64-character limit; ordinary terms keep the 12-character limit;
- the error text names the applicable limit and suggests `pattern/regex` or `criterion/check` when the real target is a file product.

Tests: `review_rubric_allows_file_path_must_include` accepts `workspace/notes.txt` and rejects an overlong path with the 64-character hint; the existing whole-sentence and long-token rejection tests still pass.

## N11 — plain-text tool calls are recovered, malformed names normalized

With review-gate on, the 4B exec model sometimes wrote a call into the answer body instead of returning structured `tool_calls`:

```text
tool_call tool.fs.write {"path":"workspace/notes.txt","content":"..."}
```

The context parser now has a compatibility fallback for `tool_call <name> <json>` / `tool_call: <name> <json>` when no structured call or `name`+`arguments` object was found. It balances the JSON object, parses it, and normalizes common aliases:

- `tool_fs_read` → `tool.fs.read`, `tool_fs_write` → `tool.fs.write`, `tool_fs_list` → `tool.fs.list`, `tool_shell` → `tool.shell`;
- `tool_fs` maps to `tool.fs.read` unless it has a `content` field (then `tool.fs.write`); bare `tool.fs` only maps to `tool.fs.write` when `content` is present, otherwise it remains an unknown tool for the existing correction path.

The review feedback system message also carries a tool-format guard: calls must go through the API `tool_calls` channel, not into the final answer. This is a compatibility recovery, not a guarantee that a 4B model will always obey the format; an unrecognized name still produces the existing unknown-tool correction.

Tests: `plain_text_tool_call_line_is_extracted`, `plain_text_tool_call_aliases_are_normalized`.

## N12 — search results have an auditable copy under `data/`

rc.4 wrote search/news/fetch artifacts only to the project workspace (`workspace/<project>/.featheagent/search/`). The retest looked under `data/` and found nothing, so the artifact was not independently auditable.

`persist_web_result` now writes both:

- workspace mirror: `workspace/<project>/.featheagent/search/<ms>-<token>-<tool>.json`, returned as `artifact` with `artifact_kind`;
- data audit copy: `data/web-artifacts/<sanitized-session>/<ms>-<token>-<tool>.json`, returned as `audit_artifact`.

A failure in either write is joined into `persist_error`; it never fails the search itself. The audit file keeps the same `tool`, `arguments`, `result`, `untrusted:true`, `saved_at_unix_ms` payload.

Test: `web_search_artifact_audit_copy_is_written`; the workspace helper test remains.

## N13 — final rubric is recorded separately

The retest found zero judge artifacts because guide failed three times. It could not tell which final rubric would have been used, or which `match`/`min_matches` settings were selected.

After a rubric is accepted and before `review.guide` is emitted, the kernel now writes:

```text
data/review-artifacts/<sanitized-session>/<ms>-rubric-final.json
```

The payload contains `role:"rubric-final"`, `session`, `model`, `temperature`, `attempt`, `at_unix_ms`, `input`, the normalized `rubric` (including `match` and `min_matches`), `hard_items`, and `judge_only`. `review.guide` gains `final_artifact`. Failed guide attempts remain available as `guide-aN`; a session that never produces an accepted rubric still has no `rubric-final`, which is the correct signal for “no rubric was selected”.

## N14 — 4B multi-task long-flow boundary (documentation only)

The rc.4 retest showed the same prompt scoring 3/4 with review-gate off and then 1/4 on a second run. This is model drift/capacity, not a deterministic kernel defect. Documentation now states:

- multi-task, long-horizon workflows should use a ≥7B exec model;
- test baselines need repeated sampling, not a single run;
- 4B results are recorded as observed, not as a regression gate.

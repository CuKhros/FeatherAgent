# FeatherAgent v1.2.1-rc.4.9 Changes

> Baseline: `v1.2.1-rc.4.8` (commit `a192ad3`)
> Source: Windows real-machine retest report for v1.2.1-rc.4.8, findings N43–N46
> Date: 2026-11-27

## Summary

The rc.4.8 retest accepted its three main targets: N42 is 5/5 clean after force-kill, N40 hits all three ML02 formula checks, and N41's four-step ML10 scoring is stable; the 9-character Chinese evidence also passed on the first try. The second write-file run failed because the judge returned an empty evidence string, not because of the length floor.

This release handles the three new findings:

- **N43 (🟠)**: empty evidence was merged into “evidence too short”, and two attempts degraded the round. An empty string is an invalid vote and must be retried separately.
- **N44 (🔴)**: the body had already been generated, but a malformed XML tool marker at the end made the provider emit an error and the round `failed`. Keep the body and downgrade the tail to `review.warn`.
- **N45 (🟠)**: the model solved ML10 correctly, announced a Python check without calling the tool, then negated its own work and stopped. The system prompt now says “either call the tool and wait, or trust the derivation you already have”.

**N46 (🟡)** is an observation: the same question produced 140–3514 characters. This release adds prompt guidance for complete derivations, no padding by repeated verification, and no premature stop; it deliberately adds no hard length gate.

## N43: empty evidence is an invalid vote

**Observed.** The second write-file run reported `审批项 c3 的 evidence 过短 ... ""`. The quoted value was empty: the judge wrote nothing. The old parser grouped an empty string with short placeholders, and two failed attempts made `review.finished(status=degraded)`.

**Root cause.** `parse_verdict` in `src/review.rs` checked `evidence_is_substantive` first, so `""` and “总结” followed the same branch. The judge-vote loop in `src/engine/mod.rs` hard-coded two attempts per vote.

**Fix.**

- `parse_verdict` now checks an empty item evidence first and returns a distinct error: `evidence 为空：该票无效...`, not “evidence 过短”; the top-level summary gets the same distinction.
- Added `review::verdict_error_is_empty_evidence`; the engine raises that vote's budget from two to three attempts only for empty evidence. Short or non-quoted evidence still gets two.
- The `[审批结果不合格]` note tells the judge that an empty value is an invalid vote, not a failed criterion, and asks for a non-empty contiguous quote from the answer.
- `review.warn.retry` and the final `judge ... 未产出合规审批` message now use the actual attempt budget.

**Verification.** New unit tests cover empty item evidence, empty summary evidence and the unchanged short-evidence failure. New integration test `review_gate_empty_evidence_retries_and_approves`: the mock judge returns empty evidence once, the retry returns a valid quote, and the round ends `approved` / `status=ok` with “evidence 为空” in `review.warn` and no “evidence 过短”.

**Boundary.** If three attempts all return empty evidence, the vote still fails and the review degrades; that is a real “judge cannot provide evidence” failure, not a hidden pass.

## N44: keep the body when only the XML tail is malformed

**Observed.** ML02 had a 727-character answer and scored 3/3, but ended with `error: XML syntax error on line 4` and `status=failed`.

**Root cause.** In `src/bin/plugin.rs`, a provider error was recovered only when the accumulated text parsed into a tool call. Otherwise the plugin emitted `error`; `run_model` returned `Err` immediately, discarding the generated body.

**Fix.**

- Both the stream `error` branch and the HTTP-error branch now record `upstream_warn` and continue to `done` when the accumulated body is non-empty and no call can be recovered. They no longer emit `error` first.
- The `done` event carries the full `text` and an optional `warn`; the engine replaces the accumulated text with `done.text` and emits `review.warn` (`source=provider`, `kind=malformed_tool_markup`).
- Added `context::parse::strip_malformed_tool_markup`, called only after a reported XML/tool-format error, to cut the trailing `<function` / `<parameter` / `<tool_call` block. Normal answers that merely demonstrate XML are unaffected.
- If the stripped result has neither text nor a structured call, the provider still fails; a pure malformed marker is not treated as success.

**Verification.** New unit test `malformed_xml_tail_is_stripped_after_content_is_kept`; new integration test `provider_malformed_xml_tail_keeps_answer_and_warns`: mock Ollama streams the 727-character body, then an XML syntax error. The final `model.message` keeps the body, contains no `<function`, emits `review.warn`, and `chat.finished.status=ok`.

**Boundary.** This only recovers a round that already produced body text. A response that consists solely of malformed markup still fails. Mock/Wine prove the protocol path, not every XML variant from a real Ollama server.

## N45: verify or trust — do not do both in prose

**Observed.** ML10 first produced `\frac{\pi}{16}`, then wrote “let me check with Python” without calling a tool, negated the derivation through a Beta-function rewrite, and ended with “sorry, this derivation is too complex”.

**Root cause.** The system prompt required a reviewable process but did not say that a stated verification must wait for a tool result, nor forbid negating an existing derivation from imagination.

**Fix.** `src/context/mod.rs` now says: if a derivation is already sound, keep it; if you choose to verify, call the tool and wait for its result; do not negate the derivation without a tool result; either call and wait, or trust what you have. It also forbids presenting a correct result and then “verifying” it with an unexecuted check.

**Verification.** `system_prompt_separates_content_output_from_file_creation` asserts the new rules verbatim.

**Boundary.** This is prompt guidance, not a guarantee for a 4B model. The real gain needs 3–5 ML10 runs on Windows.

## N46: pacing guidance, no hard length gate

The same question produced 140 / 973 / 1136 / 1550 / 3514 characters, showing both premature stops and repeated verification. A 140-character answer can still be correct, so a minimum-length gate would create false negatives. The math/proof prompt now asks for a complete process, a conclusion after the derivation, no padding by repeated verification, and no stop before the conclusion. N46 stays an observation, not a hard rc.4.9 acceptance condition.

## Compatibility and tests

- No new front-end frame, endpoint, event kind or error code. `review.warn` remains the existing event; its payload only gains `source` / `kind` / `model` / `retry`.
- The provider plugin's `done` event now carries full `text` and optional `warn`; this is the internal kernel/plugin stream protocol and the engine tolerates their absence.
- `parse_verdict` error text now distinguishes “evidence 为空” from “evidence 过短”; scripts that match the old text need updating.
- Linux: 217 tests, 216 passed, 1 ignored (public-network search); lib 87, plugin 34×2, kernel 5, TUI 6, WebUI 4×2, golden 2, integration 41 (40 passed, 1 ignored). `scripts/ci.sh` passed.
- Windows x64 cross-compiles ten exes (five Chinese + five `-en`); final byte sizes, package hash and Linux/Wine benches are in the verification report and release notes.

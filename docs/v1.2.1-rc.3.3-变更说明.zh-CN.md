# FeatherAgent v1.2.1-rc.3.3 变更说明

本候选版处理 rc.3.2 真机复测的 K1–K4。该轮已确认 J1–J3 生效：`review.warn` 的机器计数、答案不再泄漏 `cN`、`metrics.env` 证明此前的“性能退化”其实是整机内存 87–90%。但 review 门禁仍只通过 1/3，失败点转成判据设计（K1）与 7B judge 漏项（K2）。本版按报告 §10 把判据分流、正则、串行投票落到代码里。

## K1 · 判据先分流，再决定是否问模型（🔴）

**现象。** `must_not_include`、`min_points` 被送进 judge。它们成立时，正确证据只能是“答案里没有 X”，不可能是答案中连续 ≥10 字的原文；`parse_verdict` 拒收两次后整轮 degraded。`min_points` 同理。

**修法。**
- `must_include`、`must_not_include`、`min_points`、`pattern` 与新增的 `regex` 一律交给 `review.hardcheck`。这些判据确定性、零模型成本。
- 只有描述型判据（仅 `criterion`/`check`，没有硬键，标记 `judge_only`）进入 `review.judge`；judge 输入里只放这一子集。
- 描述型判据仍执行严格证据规则：必须是答案中连续 ≥10 字原文，不能抄提示词、不能写总结。
- `regex` 是真正的正则（`regex` crate，最长 200 字符，`min_matches` 1–50），guide 阶段就编译校验，坏正则不会拖到 exec 轮才爆。
- `hardcheck.pattern_engine: regex` 让旧 `pattern` 键按正则解释；默认仍是 `glob`，旧判据不受影响。独立的 `regex` 键始终按正则执行。

## K2 · 单个 judge 漏项不再拖垮整轮（🟠）

**现象。** judge 返回了 `c1`、`c3`，漏掉 `c2`；内核要求逐项齐全，重试一次仍漏，整轮 degraded。

**修法。** 缺项或格式不合格时，把具体原因和完整 id 清单回注给同一票：`必须逐项返回全部验收项，id 一个都不能少：c1, c2, c3。每条 evidence 必须是答案中连续 ≥10 字原文。` 每票最多补投一次；补投合规就继续本轮。过程仍以 `review.warn`（`第 N 票第 M 次审批不合格：…`）可见，不会静默吞掉。

## 串行投票（可选）

- `judge.votes` 只接受 **1 或 3**，拒绝 2 票以免平局；默认 1，所以 rc.3.3 不主动增加模型调用。
- 投票串行，一次只发一个模型请求，峰值模型并发仍为 1。温度依次为 base、base+0.05、base+0.10，封顶 0.2，制造轻度独立性又不至于把 JSON 打崩。
- 聚合只支持 `majority`，不提供 `all`/AND。即使某票已失败也要把票投完；同一项多数 pass 才算通过。
- `judge.early_stop_on_agreement: true` 时，前两票逐项 pass/fail 完全一致就跳过第三票。
- `config.set` 会拒绝非法的票数与聚合方式。

## K3 · 热启动看中位，也看尾部（🟡）

门禁原本就是 1 次预热丢弃 + 5 次取中位。rc.3.3 在 JSON 增加 `boot_ms_p90` 与 `boot_sample_count`，人类可读输出打印 P50/P90 和样本数。单次 85 ms 不会再藏住整个分布；门禁仍用 P50 对 Windows 100 ms、Linux 20 ms。

## K4 · 内存压力只标注可信度，不判红（🟡）

- `metrics.env` 在 Linux 也输出 `mem_load_pct`（用 `(MemTotal - MemAvailable) / MemTotal` 近似），Windows 继续用 `dwMemoryLoad`。
- 新增 `reliability`（`high` / `medium` / `low`）；`mem_load_pct >= 85` 时追加 `note`：`整机内存占用 …%，启动/写入读数可能偏高，仅作参考、不作门禁失败`。
- 门禁布尔值不变。压力机只标注，不误判；发布基线仍应在刚重启的机器上取。

## 设置契约

`plugins/review-gate/plugin.json` 从 9 个字段增至 14 个，仍由内核原样转述，TUI 与 WebUI 通用渲染：

| 键 | 取值 | 默认 |
|---|---|---|
| `criteria_routing` | `auto` / `hardcheck_only` / `judge_only` | `auto` |
| `hardcheck.pattern_engine` | `glob` / `regex` | `glob` |
| `judge.votes` | `1` / `3` | `1` |
| `judge.aggregation` | `majority` | `majority` |
| `judge.early_stop_on_agreement` | 布尔 | `true` |

`hardcheck_only` 不评估描述型判据，按确定性判据放行并打 `review.warn` 说明有几条未评估。`judge_only` 是保留的旧行为，仅用于对照/调试；它会重现 K1 的冲突，不应在生产环境使用。

## 兼容性

- 没有改动 wire 消息、provider、storage、tool 或 IPC 帧。
- `review.hardcheck` 与 `review.judge` 都是插件内部契约，两端都由内核掌握，输入变化不影响前端。
- `review.warn` 文本有变化：`min_points` 软判据改为“按软判据接受…”，另加“N 条描述型判据未评估”；事件码与字段不变。
- 默认 `auto` 是有意的行为变化：只有硬判据的 rubric 不再调用 judge；含描述型判据的 rubric 调一次。这正是 K1 的目的。
- bench JSON 新增 `boot_ms_p90`、`boot_sample_count` 与 `env.reliability` / `env.note`，忽略未知字段的消费方不受影响。

## 验证

- Linux：118 个测试，117 通过，1 ignored（`local_web_search_tool_via_kernel`，需公网）。分布：62 lib、17 plugin、2 kernel、3 TUI、3 WebUI、2 golden、29 integration。rc.3.2 为 116/115。
- 新增覆盖：`review_gate_routes_negative_criterion_to_hardcheck`、`review_gate_missing_description_item_is_reinjected`、`review_rubric_accepts_regex_and_rejects_invalid_one`；设置测试增加 `judge.votes=2` 拒绝与新枚举字段写入。
- `cargo fmt --check`、`cargo clippy --locked --all-targets` 通过。
- Windows x64 交叉编译完成，PE 依赖均为系统 DLL；自动化仍只在 Linux 跑，Windows 结论以真机为准。
- Linux release bench 三次：热启动 P50 1.180 / 1.148 / 1.151 ms（P90 1.183 / 1.140 / 1.145 ms），冷启动 3.391 / 3.294 / 2.940 ms，RSS 3,456–3,584 KiB，写入 P95 2.678–4.220 µs，组装 P95 0.138–0.176 ms，RPC P95 0.038–0.053 ms，二进制 2,516,416 B（2.400 MiB），门禁全绿，`env.mem_load_pct` 16–17%，`reliability: high`。

## 仍需 Windows 真机确认

1. 真实 7B 跑一条 `must_not_include`：不再出现“evidence 不是答案原文”，负向判据由 hardcheck 结案。
2. 一条描述型 + 一条硬判据：judge 只看到描述型；故意漏项时应回注补投，而不是 degraded。
3. 可选 `judge.votes: 3`：通过率稳定，且峰值模型并发不超过 1。
4. `bench --json` 含 `boot_ms_p90`、`boot_sample_count`、`env.mem_load_pct`、`env.reliability`；≥85% 时有 note 且不会把门禁判红。
5. 此前遗留：真实 Ollama 模型下拉、ConPTY Enter 保存、Windows Terminal 权限弹窗、S3 t6 单次调用。

# FeatherAgent v1.2.1-rc.2 Changes

Date: 2026-11-24

`v1.2.1-rc.2` is a patch release for the v1.2.1-rc.1 Windows real-hardware report. R1 and the review-gate flow remain as reported; this release fixes the P0 provider regression and the two configuration issues found in the same retest.

## 1. P0: empty provider request body (fixed)

### Symptom

Every `provider-ollama` request carried an empty body (`Content-Length: 0` on Windows), so real Ollama returned `400 missing request body`. `/api/chat` and `/api/embed` were both affected; the response parser was fine.

### Root cause

The HTTP request builder inserted the optional Authorization header into an already formatted header block:

```text
Content-Type: application/json\r\n{Authorization or empty}\r\nContent-Length: ...
```

When `provider_api_key` was empty, the empty Authorization produced a blank line **before** `Content-Length`. That blank line terminates the HTTP headers, so the server never saw `Content-Length` or the JSON body. The body was still written, but the peer treated it as the next request / ignored it. With a non-empty key the bug was hidden.

### Fix

`src/net.rs::build` now appends headers line by line: `Content-Length` is always emitted before the optional `Authorization`, and the terminating blank line is written exactly once, after all headers. Both `post_json_auth` and `stream_post_lines_auth` share this builder.

### Regression tests

- `net::tests::empty_bearer_preserves_headers_and_body`: captures the raw request for `None` and `Some("")` keys, asserts `Content-Length: 2`, the body `{}`, and no blank line before `Content-Length`.
- `ollama_native_chat_without_key_still_sends_body`: real kernel + mock Ollama, empty key; asserts `/api/chat` has `Content-Length`, `messages`, `stream:true`, and `/api/embed` has `model` and `input`.

Linux live echo reproduction now records a non-empty `/api/chat` request. With the CLI model `qwen3.5:4b`, the body included `"model":"qwen3.5:4b"` and `Content-Length: 6842`; `model.delta` / `model.message` returned `ECHO_OK`.

## 2. P1: review-gate temperature ranges are now enforced (fixed)

`validate_config` previously checked the three role temperatures only when `review_gate.enabled=true`, so `config.set` accepted `judge=0.8` while the gate was off, persisted it, and only rejected it on a later enable.

Now the ranges are schema-level constraints regardless of `enabled`:

| Config path | Allowed |
|---|---|
| `review_gate.guide.temperature` | `[0.2, 0.5]` |
| `review_gate.exec.temperature` | `[0.6, 1.5]` |
| `review_gate.judge.temperature` | `[0.0, 0.2]` |
| `review_gate.max_rounds` | `[1, 5]` |

Errors include the path, the submitted value, and the allowed interval, for example:

```json
{"jsonrpc":"2.0","id":3,"error":{"code":-32602,"message":"review_gate.judge.temperature=0.8 超出允许区间 [0.0, 0.2]"}}
```

Invalid values are rejected before `cfg.save`, so `config.json` is not modified. The WebUI now validates the three temperatures and round count even when the enable checkbox is off; the backend remains the final gate.

If an rc.1 `config.json` already contains an out-of-range temperature, rc.2 does not silently clamp it: the next `config.set`/enable attempt is rejected, and the file must be corrected (WebUI or JSON) before review-gate can be enabled.

## 3. P2: effective config is visible at startup (fixed)

`serve` now prints an explicit effective-config line after the banner:

```text
effective model=qwen3.5:4b provider=provider-ollama base_url=http://127.0.0.1:11499
  (model_source=cli, provider_source=cli, base_source=cli)
```

When a CLI flag differs from `config.json`, it also emits a warning:

```text
warn: --model 覆盖 config.json 的 qwen2.5:7b（实际使用 qwen3.5:4b）
```

The runtime value is the CLI value; the warning makes the precedence visible instead of silently using the persisted value. `config.get` returns the same effective values.

### Related fix: embeddings use the active model

During reproduction, `/api/embed` still requested the provider default `qwen2.5:7b` while chat used `qwen3.5:4b`. `recall` and `index_user_text` now pass `cfg.model` in the embed request, and the provider uses it. This prevents an Ollama embedding call from targeting a model the user did not select.

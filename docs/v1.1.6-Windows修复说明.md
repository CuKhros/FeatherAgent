# FeatherAgent v1.1.6 Windows 修复说明

> 依据：《Windows 真机复测报告 v1.1.5》（2026-11-22）
> 基线：`v1.1.5`，提交 `4addc48`
> 目标平台：Windows 10/11 x64（交叉编译 + Wine 冒烟；真机结论仍需用户复测）

## 0. 先说结论

v1.1.5 报告中的 **NEW-E / NEW-F / NEW-G 已在真机确认修复**：业务错误不再误熔断、`/workspace/...` 正常落盘、S3 严格口径与写盘结果一致；bench 6/6、S3 工具执行 4/5、单任务 6.6–8.6 s。

## 1. NEW-H：启动无输出、约 60 s 才可用

### 现象

- `serve` 启动后 `_serve.log` 恒为 0 字节；`runtime\ipc\endpoint` 约 60 s 才出现。
- 期间 `chat` 报“连接内核失败（...featheragent.sock）: 系统找不到指定的文件”，把“启动中”误报成“通道挂了”。
- 错误文案指向 `.sock`，但 Windows 实际走命名管道。

### 根因

- `serve` 的 banner 写在 `Kernel::new` **之后**，且走 stderr。首次启动要扫描/登记内置插件（Windows 实时防护会扫描每个 exe），这段时间 stdout 没有任何内容；只重定向 stdout 的日志自然是 0 字节。
- 启动没有 `starting` / `ready` 状态文件，`chat` 只能拿到裸 `CreateFileW` 的 os error 2，无法判断内核是否正在启动。

### 修法

- `serve` 在 `Kernel::new` **之前**打印 banner，并显式 `flush`；随后分阶段打印：
  - `serve: 初始化内核（首次启动需登记内置插件，Windows 首次可能 30–60s）`
  - `serve: 内核初始化完成（N ms）`
  - `serve: 开始监听 ...`
  - `serve ready: 1.1.6` + endpoint/runtime
- 启动即写 `runtime/ipc/starting`（含 pid、版本、开始时间）；监听成功后写 `runtime/ipc/ready`，删除 `starting`；退出时删除 `ready`/`endpoint`。
- `chat` 连接前检查就绪状态：
  - 有 `starting` 且未超 180 s → **“内核未就绪（启动中，约 Ns）……请等 serve 输出 serve ready 或 ready 出现”**；
  - 有 `starting` 超过 180 s → 提示进程可能已退出，检查 serve 日志；
  - 无 `ready`/`starting` → 提示先启动 `serve`；
  - 有 `ready` 但仍连不上 → 报真实连接错误，并提示端点繁忙/内核重启。
- `chat` 连接最多等 5 s，避免脚本一启动就误判；仍不阻塞到 60 s。

### 验证

- Linux 实测：serve 启动 0.4 s 内日志已出现 banner、初始化、监听、`serve ready`；`runtime/ipc/ready` 存在。
- 无内核时 `chat` 输出“内核未就绪：未发现 .../ready 或启动标记。请先运行 ...”。
- Windows 真机仍需确认首次 30–60 s 场景；Wine 的启动时序不代表真机。

## 2. NEW-I：`config.set` 签名不符、必须整份覆盖

### 现象

设计文档写 `config.get / set(path, value)`，实测只接受 `{value: 完整 Config}`；`{path:"temperature",value:0.42}` 报 `expected struct Config`。两个前端同时保存会互相覆盖。

### 修法

- `config.set` 支持三种形态：
  - **单字段原子更新**：`{"path":"temperature","value":0.42}`，支持 `temperature` 或 `/temperature`；
  - **部分字段合并**：`{"patch":{...}}`（WebUI/TUI 继续使用）；
  - 兼容旧调用：`{"value":{...完整 Config...}}`。
- 新增 **`config.replace`**：`{"config":{...完整 Config...}}` 才表示整份替换，避免把“保存一个字段”误当 replace。
- `Kernel` 新增 `config_lock: Mutex<()>`；`set_config` / `set_config_path` / `replace_config` 全部在锁内完成“读 → 改 → 校验 → 原子写 → 更新内存 → 发 `config.changed`”，并发保存不再丢更新。
- `config.get` 的 `path` 同时接受 `temperature` 与 `/temperature`。
- 未知字段路径返回 `配置项不存在: xxx`；类型错误仍由 serde 拒绝，温度/窗口/回合/provider 校验沿用 v1.1.5。

### 验证

- `cargo test` 集成用例 `config_api_applies_and_lists_models` 已扩展：
  - `config.set {path:"temperature",value:0.45}` → `config.get {path:"temperature"}` 读回 0.45；
  - 未知字段被拒；
  - 两个线程并发改 `max_turns` / `context_window`，最终两者都保留；
  - `config.replace` 整份替换后读回 0.55。

## 3. NEW-J：S3 把预期业务错误算成执行失败

### 修法

`tools/s3_batch.py` 从“成功/失败”两档改为三档：

| 档位 | 判定 |
|---|---|
| `OK` | 有 `tool.result`、未 denied、result 无 error，且无 `tool.error`/`tool.failed` |
| `预期失败` | 任务标记为负样本（t6 读不存在文件），产生业务错误，且最终答复正确（包含“不存在”） |
| `ERR` | 其余情况；包括真失败、预期错误但答复不正确 |

汇总同时输出“工具执行成功（严格口径）”“预期业务错误且答复正确（预期负样本 N 个）”“真失败”，不再让 t6 把成功率拖成 4/5 却看起来像失败。

### 验证

- 用伪造 `featheragent` 事件流在 Linux 离线跑通：t1/t2/t3/t5 `OK`，t4“未调用”，t6“预期失败”；统计为工具执行成功 4/5、预期业务错误且答复正确 1/1、真失败 0/5，写入校验 `workspace/w1.txt` 存在 `HELLO_W_99`。
- Windows 真机需按 `START-HERE.md` §7 重跑 S3，确认真实模型下 t6 仍显示“预期失败”。

## 4. WebUI 模型下拉只显示一项

### 现象

设置页模型输入框使用原生 `<input list="...">` + `<datalist>`。当前配置里已有模型名（如 `qwen3.5:4b`），浏览器会按输入值过滤建议列表，打开下拉时只显示匹配的那一项；实际 `provider.models` 已返回全部模型。

### 修法

- 移除 `datalist`，改为输入框 + 真正的 `<select id="cfg-model-select">`：
  - 第一项“选择已发现模型（N）”；
  - 后续列出 `provider.models` 返回的全部模型（去重、排序）；
  - 选中后写回 `#cfg-model` 输入框，仍可手填；
  - 输入框内容变化时同步下拉选中状态。
- `renderModelList` 不再受当前输入值过滤；`cfgModels` 去重后再渲染。
- 后端 `provider.models` 也对 `models` 数组去重，避免同一模型重复显示。
- 静态资源单测新增 `cfg-model-select`、`renderModelList` 断言，并断言旧 `cfg-model-list` 已移除。

### 验证

- Linux 浏览器 + mock Ollama 返回 3 个模型（`qwen3.5:4b`、`llama3.1:8b`、`deepseek-r1:7b`）：
  - 下拉实际 DOM 选项为“选择已发现模型（3）” + 3 个模型，共 4 项；
  - 选择 `llama3.1:8b` 后输入框同步为 `llama3.1:8b`；
  - 保存后 `data/config.json` 的 `model` 为 `llama3.1:8b`。
- 真实 Windows 仍需点选确认；浏览器原生控件行为与 Chromium 版本有关。

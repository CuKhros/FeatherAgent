# FeatherAgent 1.2.1-rc.3 Changes

> Date: 2026-11-24 · Base: `v1.2.1-rc.2.1` · Type: architecture (plugin-declared settings) + review-gate quality follow-up

This release makes plugin settings a **declaration**, not a UI special case: a plugin states its settings schema in its own manifest, the kernel relays it verbatim, and every front end renders it generically. It also closes the four review-gate/S3 findings (H1–H4) from the rc.2.1 real-hardware retest. Review-gate remains experimental and disabled by default; provider endpoints and the channel wire format are unchanged apart from one additive RPC.

## Architecture · plugin-declared settings

### A-01 · Settings are declared by the plugin, relayed by the kernel, rendered generically

- Every plugin may declare `manifest.settings` in `plugins/<name>/plugin.json`:
  - `root` — config path the fields live under (default `plugin_settings.<plugin name>`);
  - `title`, `description` — what the settings page shows above the form;
  - `fields[]` — `key`, optional absolute `path`, `label`, `type`, `default`, `description`, `placeholder`, `min`, `max`, `step`, `options`, `secret`.
- `type` is restricted to `bool | int | number | string | enum` so any front end (TUI, WebUI, a future GUI) can render it without plugin-specific code. No plugin ships UI code, and adding a plugin does not require touching any front end.
- `feather-plugin` handshakes with `settings: None` on purpose; the manifest file is the single source of truth, so the two can never drift. The kernel reads the manifest at install/refresh time and persists it in the registry.
- `src/proto/types.rs`: `SettingsSchema`, `SettingField`, `SettingsSchema::root_for()`, `SettingField::path(root)`, `SettingField::validate()`.
- `src/runtime/registry.rs`: `Entry.settings` is populated by `install()`; `scan_builtin()` backfills old entries that were registered before this release (`update_settings` + `read_settings`).

### A-02 · New RPC `plugin.settings` (additive)

- `plugin.settings {name}` returns `{name, root, title, description, fields[], values{}, defaults{}}`; an undeclared plugin returns a business error (“插件 X 未声明设置项”) instead of an empty form.
- Front ends call it only when a plugin page opens, so the settings page does not depend on a plugin process being alive.

### A-03 · Kernel-side validation, same rules for every front end

- `Config.plugin_settings: BTreeMap<String, Value>` is the fallback namespace for plugins that declare no `root`.
- `declared_settings()` expands the registry schema into `(absolute path, field)` pairs; `validate_plugin_settings()` checks type, range, and enum membership, and rejects keys under `plugin_settings.<name>` that the plugin never declared.
- `config.set` accepts a first write to a declared path (parent objects are created), while undeclared paths keep failing with “配置项不存在”. A typo therefore fails at the kernel, not silently in one UI.

### A-04 · TUI and WebUI render the declaration

- TUI: the general settings page has 11 fields again (provider … auto-allow, save, cancel); every plugin row in the sidebar opens a page built from `plugin.settings`, with the enable toggle, declared fields, save, and cancel. Text, integer, number, bool, and enum fields are all editable with the declared range shown.
- WebUI: the general page no longer contains review-gate or search blocks; the plugin page renders the manifest summary first, then the declared form (checkbox, number, text, select) and saves through `config.set`.
- Both front ends show the plugin name in the sidebar (category only as secondary text), so a plugin with an unusual category is not mistaken for another plugin.

## Fixed · review-gate and S3 (rc.2.1 retest)

### H1 · Rubric degenerated into “guide writes the answer, exec copies it”

- Symptom: all three items were full sentences of the answer; seven model calls produced an answer that simply repeated the guide text, and the gate reported approved.
- Cause: `must_include` was allowed to be a 1–40 character phrase including whole sentences, and only `must_include` existed as a criterion kind, so “contains the sentence” was the only thing measured.
- Fix:
  - `review.parse_rubric` now accepts 2–5 items, `must_include` ≤20 characters, and rejects sentence-like phrases (sentence-final punctuation, or ≥12 characters containing connectives such as 是/的/了/和/并/而/为);
  - every rubric needs at least one `must_include` and at least one **non-substring** criterion (`must_not_include`, `min_points`, `pattern`);
  - `review.hardcheck` evaluates all four kinds deterministically before the judge runs: literal substring, banned phrases, point count (markdown bullets, numbered lists, 顿号 numbering), and glob patterns (`*`, `?`, `|`, case-insensitive, zero new dependencies);
  - the guide prompt now asks for 2–5 checkable criteria, forbids writing the answer, and requires at least one non-substring criterion.

### H2 · Judge “evidence” quoted the prompt instead of the answer

- Symptom: the judge satisfied the ≥10 character rule by echoing prompt text, so every item passed without reading the answer.
- Fix: `review.parse_verdict` now receives the answer and requires each item's evidence **and** the top-level summary to be a verbatim contiguous window (≥10 characters, normalized for markdown marks and whitespace) of the answer. Prompt echoes, “总结”, “ok”, and paraphrases are rejected as judge failures, which then follow the existing retry policy.

### H3 · Malformed tool names produced an unreadable RPC error

- Symptom: the model emitted `tool.fs` / `tool.read_file`; the kernel forwarded the name to the tool plugin and surfaced `rpc40401`, with no list of real tool names.
- Fix: `execute_tool` checks the name against `available_tools(&session.locked_tools)` first and returns a business error such as `未知工具 tool.fs。可用工具：tool.fs.read, …`. It is a normal `tool.error` for the model, not a plugin crash, so no circuit breaker is tripped.

### H4 · S3 t5 did not call a tool and t6 called it repeatedly

- Fix: `tools/s3_batch.py` t5 now states “must call `tool.fs.read` first; do not answer from context”; t6 states “call the read tool once; if it fails, report the failure and do not retry or switch paths”. This makes the S3 rate reproducible instead of dependent on prompt luck.

## Compatibility

- `manifest.settings` is optional; plugins without it still appear in the sidebar with an enable toggle and a “未声明设置项” page.
- `plugin.settings` is a new method; existing clients are unaffected. `chat.finished`, `plugin.list`, and `config.*` keep their semantics.
- Config migration is automatic: unknown `plugin_settings.<name>` keys are left in place but are not writable through `config.set` unless declared.

## 2. 关键设计变化

### 2.1 命名管道不再是“单句柄双线程”

v1.1.1 的 Windows `Stream` 内部是 `Arc<PipeHandle>`，reader 线程和 writer 线程共享同一个 HANDLE。Windows 同步句柄上挂起的 `ReadFile` 会阻塞同一句柄上的 `WriteFile`，于是 `initialize` 的响应永远发不出去；Wine 的管道并发语义不同，所以 Wine 冒烟没暴露。

v1.1.2：

- `CreateNamedPipeW` / `CreateFileW` 都带 `FILE_FLAG_OVERLAPPED`；
- 每次 `ConnectNamedPipe` / `ReadFile` / `WriteFile` 新建 `OVERLAPPED` + 手动重置事件，`GetOverlappedResult(..., 1)` 等待；
- `try_clone()` 用 `DuplicateHandle(DUPLICATE_SAME_ACCESS)` 拿独立句柄；
- `PIPE_REJECT_REMOTE_CLIENTS`，DACL 仍是默认同用户；
- 读端 `ERROR_BROKEN_PIPE` / `ERROR_PIPE_NOT_CONNECTED` 按 EOF。

### 2.2 端点发现

服务端 `Server::run` 绑定成功后写 `<root>/runtime/ipc/endpoint`：

- Windows：`\\.\pipe\featheragent-<blake3(path)[..16]>`
- Unix：`<root>/runtime/ipc/featheragent.sock`

管道名哈希键统一小写 + 反斜杠，避免安装根大小写/分隔符导致两端算出不同名字。

### 2.3 编码协商

- 默认 `msgpack`（named map），与 v1.1.1 线上行为一致；
- `--codec json` 时读写都用 JSON，`initialize.result.codec` 返回 `json`；
- GUI/TUI 内置客户端固定 MsgPack；JSON 只作为第三方调试/参考实现；
- 帧头始终是 `u32 LE length + body`，上限 64 MiB。

## 4. 未验证 / 风险

- **真实 Windows 上的 overlapped 管道并发、异常断开、TUI ConPTY、GUI `--app`、网络盘拦截**：需用户按 `START-HERE.md` 复测。
- **Windows `bench` 性能**：v1.1.2 只修了停止/可观测性，没有改变 `FlushFileBuffers` 策略；报告中的 464 ms/次预计仍会出现。
- **Wine 6 的 `bcryptprimitives.dll` 缺失**：本地冒烟用临时 stub 旁挂，**不进入发布包**；真实 Windows 10/11 系统自带。
- **S3 真实模型指标**：`chat` 已提供脚本通道，但 `qwen3.5:4b` 的实际延迟/内存仍需用户在真机跑。

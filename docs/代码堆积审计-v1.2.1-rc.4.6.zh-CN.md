# FeatherAgent v1.2.1-rc.4.6 — 代码堆积审计

> 审计对象：`v1.2.1-rc.4.5` 的 `main`（提交 `4dc2ded`）
> 对比基线：`v1.2.1-rc.3.6` 的生成器形态、review 解析形态、`bench --json` 形态
> 审计时间：2026-11-26
>
> 这份文档回答一个问题：**rc.4.5 里哪些地方已经不是在改架构，而是在往旧结构上叠特例？** 本轮只重构证据最明确、且与 N32–N35 直接相关的部分；没有把“文件长”一律当成“屎山”，也没有做全仓重写。

## 1. 判定标准

一个位置被列为“堆积”，至少要满足下面一条，并且能指到具体证据：

1. **同一语义有多条实现路径**，且其中一条已经不可达（修一个分支、忘了删旧分支）。
2. **生成物被手工修改**，生成器长期失败，源码与生成物不再同构。
3. **一个字段/对象混放多种语义**，消费者只能靠约定猜，新增字段就会误判。
4. **同一个常量在多个调用点硬编码**，配置层没有对应字段，改行为必须改代码。
5. **中英/前后端双份维护**，但没有结构校验，功能会单边漂移。

单纯“函数长、文件大”不自动算堆积；但如果它同时承载解析、校验、重试、提示词拼装，就会在下一轮继续长分支。

## 2. 审计结论：五处真实堆积

### P1（最高）中英 Rust UI 生成链失效，生成物变成手改文件

`scripts/gen-en-ui.py` 最后一次完整通过是 `v1.2.1-rc.3.6`：

| 版本 | `tui.rs` 中文字面量 | `kernel.rs` 中文字面量 | 翻译表 | 生成器 |
|---|---:|---:|---|---|
| rc.3.6 | 166 | 72 | 166 / 72 | 通过 |
| rc.4 | 170 | 74 | 未同步 | 失败 |
| rc.4.5 | 170 | 76 | 未同步 | 失败 |

生成器用“中文字面量集合 == 翻译表条数”做断言。rc.4 起新增中文没有补翻译，断言直接失败；之后 `tui_en.rs`、`kernel_en.rs` 就变成**手工维护的生成物**。rc.4.5 的 N30 甚至在 `kernel_en.rs` 里单独内联实现，和 `kernel.rs` 不同构。

这不是“翻译没跟上”的小问题，而是**同一份 UI 逻辑有两个事实来源**：中文源和英文生成物都可以被手改，下一轮任何中文改动都会继续分叉。

处理：以 rc.3.6 的 166/72 条旧映射为基线，按当前 `sorted(zh)` 顺序重建 `scripts/en-ui/tui_en.py` 与 `kernel_en.py`，补齐 rc.4/rc.4.5 新增条目；重新生成后两文件无中文残留。`gen-en-ui.py` 只负责 Rust UI，不再假装能生成 WebUI。CI 增加“重新生成后工作树必须无 diff”，把手改生成物挡在门外。

### P2 review 解析层：3,028 行单文件 + 430 行单函数 + 不可达分支

`src/bin/plugin.rs` 原来 3,028 行，`parse_rubric_with_input` 单函数约 430 行。N29 在函数开头新增 `file_task` 分支并 `continue`，但函数后半段还保留一整段 `if file_task { ... } else { ... }`——其中 `file_task` 分支永远不可达。也就是说：**修了 N29，却留下 N29 之前的分支继续吃维护成本**。

处理：抽出 `src/review.rs`（924 行），只放纯函数：JSON 容错、判据归一化、占位符/主观判据识别、`parse_rubric`、`parse_rubric_with_input`、`parse_verdict`、`evidence_quotes`。`plugin.rs` 只保留 adapter 调用，从 3,028 行降到 2,219 行（-809）。`parse_rubric_with_input` 重排为“循环开头统一构造基础 `norm`；`file_task` 只保留一个早分支；后半段只处理普通任务”，不可达的第二个 `file_task` 分支删除。

### P3 `bench --json` 的 `gates` 混放判定值、状态、阈值和可信度

rc.4.5 的 `gates` 同时有：

- 判定布尔值：`binary_le_8mb`、`rss_le_15mb`、`*_lt_*`；
- 平台字符串：`platform`；
- 可信度字符串：`reliability`；
- 状态字符串：`boot_gate_status`、`write_gate_status`；
- 原始读数布尔值：`boot_gate_raw`、`write_gate_raw`；
- 阈值：`boot_limit_ms`、`write_limit_us`。

消费者按“数 `gates` 里的 False”判失败时，会把 `write_gate_raw=false` 当成失败——N34 就是这么来的。根因不是字段命名，而是**对象没有语义边界**。

处理：`gates` 只保留布尔判定项；新增 `diagnostics` 放平台、原始读数、状态、阈值、可信度和模式；`advisory_gates` 只放建议项。`scripts/ci.sh` 增加“gates 必须全为布尔”的断言，并把 `write_gate_status/raw` 的读取位置改到 `diagnostics`。

### P4 输出上限 512 在两个调用点硬编码，配置层没有字段

`ModelProfile.max_output` 在引擎两处硬编码为 512，`Config` 没有输出上限字段，provider 请求也从未传 `num_predict`/`max_tokens`。本地模型模板可能再叠一层很小的默认上限。N33 的 M15 只有 136 字、M20 只有 390 字——390 个中文字大约就是 500 token 量级，和 512 的硬编码对得上。

处理：`Config.max_output` 默认 2048，允许 128–8192；两处 `ModelProfile` 改为读 `cfg.max_output`；`run_model` 与 review 调用都把它传给 provider；Ollama 写 `options.num_predict`，OpenAI 兼容写 `max_tokens`。正常对话的 `ModelMessage` 增加 `truncated`，三段校验遇到 `finish=length` 直接报错重试，不再把半截输出当有效结果。

### P5 WebUI 英文包是手工 bundle，且已经漏掉附件发送

`web/app.en.js` 与 `web/index.en.html` 不是生成物，是独立维护的 bundle；`gen-en-ui.py` 的 Web 部分同样因为字符串数量不一致而失败。审计还发现英文 `send()` 缺少附件发送逻辑，英文包会丢附件——这是典型的“双份维护、没有结构校验”。

处理：明确 WebUI 英文为手工 bundle，`gen-en-ui.py` 不再处理 Web；新增 `scripts/check-en-web.py` 校验四件事：英文 JS 字面量无中文、中英函数名/元素 id/RPC 方法集合一致、英文 HTML 元素 id 与中文一致、`lang="en"` 且引用 app 脚本。补回附件发送、`file.attach` 60s 超时和三处中文残留。

## 3. 本轮不动的部分

以下位置也长，但没有满足第 1 节的五条标准，或者改动收益低于回归风险，本轮保持原状：

| 位置 | 行数 | 判断 |
|---|---:|---|
| `src/engine/mod.rs` | 3,712 | 会话、工具循环、review 编排、提示词都在一个模块；有继续拆的空间，但没有“不可达分支/双实现”证据，留到专门的重构轮 |
| `src/bin/tui.rs` | 3,222 | TUI 状态机与渲染耦合；本轮只保证生成链恢复，不做交互层重写 |
| `src/bin/plugin.rs` | 2,219 | 解析层已抽出；provider/tool/review 三角色仍在一个二进制里，下一步可按角色拆模块 |
| `src/review.rs` | 924 | 新边界，先稳定一轮；暂不再拆 |
| `web/app.en.js` | 1,134 | 手工 bundle + 结构校验是当前成本最低的方案；运行时 i18n 是更大的产品决策，不在本轮 |

## 4. 结果与验证

- `src/bin/plugin.rs` 3,028 → 2,219 行；`src/review.rs` 924 行。
- `scripts/gen-en-ui.py` 重新生成 `tui_en.rs` 3,207 行、`kernel_en.rs` 1,458 行；连续运行两次哈希一致；无中文残留。
- `scripts/check-en-web.py` 输出 `WebUI English bundle OK`。
- `scripts/ci.sh` 增加生成物一致性、Web bundle 结构和 `gates` 全布尔检查。
- Linux 全量 **206 项：205 通过、1 ignored**（`local_web_search_tool_via_kernel` 需公网）。rc.4.5 基线为 201 项（200 通过 + 1 ignored），本轮净增 5 个通过项。
- 本轮仍未在真实 Ollama/Windows 上复测 N32/N33/N35；Wine 与 Linux 单测不能替代真机结论。

## 5. 后续建议

1. 下一轮如果继续拆 `plugin.rs`，按角色拆成 `provider/`、`tools/`、`review_adapter/` 三个模块，而不是继续在单文件里加 `match` 分支。
2. `engine/mod.rs` 的拆分应以“会话循环 / 模型调用 / review 编排 / 提示词”为边界，先加回归测试再动文件。
3. WebUI 英文包要么维持“独立 bundle + 结构校验”，要么做运行时 i18n；不要回到“生成器生成一半、手改一半”。
4. 每次新增 `bench` 字段前先问：它是判定值、诊断值还是建议值？放错对象就会制造下一个 N34。

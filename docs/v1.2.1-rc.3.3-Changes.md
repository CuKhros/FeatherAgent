# FeatherAgent v1.2.1-rc.3.3 changes

This candidate fixes K1–K4 from the Windows real-hardware retest of `v1.2.1-rc.3.2`. That retest re-verified J1–J3: `review.warn` carried the expected machine count, answers no longer leaked `cN` ids, and `metrics.env` showed the earlier “performance regression” was a host at 87–90% memory. The gate still approved only 1/3 rounds, but the failures had moved: the criteria themselves fought the “evidence must be answer text” rule (K1), and a 7B judge that omitted one item degraded a whole round (K2). This release implements the routing and voting design in §10 of the report.

## K1 · Criteria are routed before the judge (🔴)

**Symptom.** A `must_not_include` or `min_points` criterion was sent to the judge. When it passed, the only honest evidence was “the answer does not contain X”, which can never be a verbatim ≥10-character window of the answer. `parse_verdict` rejected it twice and the round degraded. The same conflict hit `min_points`.

**Fix.**
- `must_include`, `must_not_include`, `min_points`, `pattern`, and the new `regex` are evaluated by `review.hardcheck` only. They are deterministic and cost zero model calls.
- Only description-type items (`criterion`/`check` without a hard key, marked `judge_only`) go to `review.judge`; its input now contains just that subset.
- Description-type items keep the strict evidence rule: a contiguous ≥10-character window copied from the answer, never the prompt, never a summary.
- `regex` is a real regular expression (`regex` crate, 200-character limit, `min_matches` 1–50) validated during the guide step, so a bad pattern is rejected before the exec round.
- `pattern_engine: regex` makes the existing `pattern` key a regular expression; the default stays `glob` so old rubrics keep working. A separate `regex` key always uses regular-expression semantics.

## K2 · One missing judge item no longer degrades the round (🟠)

**Symptom.** The judge returned `c1` and `c3` but omitted `c2`; the kernel required every item, retried once, and still degraded the whole round.

**Fix.** A malformed or incomplete verdict is now reinjected into the same vote with an explicit list: `必须逐项返回全部验收项，id 一个都不能少：c1, c2, c3。每条 evidence 必须是答案中连续 ≥10 字原文。` The retry stays inside the vote (at most one reinjection per vote); a compliant verdict then continues the round. The failure is still visible as `review.warn` (`第 N 票第 M 次审批不合格：…`) instead of being swallowed.

## Serial voting (opt-in)

- `judge.votes` accepts **1 or 3**; 2 is rejected to avoid a tie. The default remains 1, so rc.3.3 does not add model calls unless the operator opts in.
- Votes run **serially**, one model call at a time; peak model concurrency stays 1. Temperatures are base, base + 0.05, base + 0.10, capped at 0.2, to create mild independence without destabilising JSON.
- Aggregation is `majority` only; `all`/AND is not supported. Every vote is collected even when an early vote fails, and an item passes only when more votes say pass than fail.
- `judge.early_stop_on_agreement: true` stops after two votes whose per-item pass/fail pattern is identical.
- `judge.aggregation: majority` is the only accepted value; invalid combinations are rejected by `config.set`.

## K3 · Warm boot is judged by median, with tail visible (🟡)

The gate already used 1 warm-up + 5 measured boots and the median. rc.3.3 adds `boot_ms_p90` and `boot_sample_count` to the JSON and prints `P50/P90` plus the sample count. A single 85 ms boot no longer hides the distribution; the gate still uses P50 against 100 ms on Windows, 20 ms on Linux.

## K4 · Memory pressure is a reliability note, not a red gate (🟡)

- `metrics.env` now reports `mem_load_pct` on Linux as well as Windows (Linux uses `(MemTotal - MemAvailable) / MemTotal`).
- It also reports `reliability` (`high` / `medium` / `low`) and, when `mem_load_pct >= 85`, a `note`: `整机内存占用 …%，启动/写入读数可能偏高，仅作参考、不作门禁失败`.
- Gate booleans are unchanged. A loaded host is annotated, not failed; the release baseline should still be taken on a restarted machine.

## Settings contract

`plugins/review-gate/plugin.json` grows from 9 to 14 declared fields. The kernel relays them; TUI and WebUI render them generically:

| Key | Values | Default |
|---|---|---|
| `criteria_routing` | `auto` / `hardcheck_only` / `judge_only` | `auto` |
| `hardcheck.pattern_engine` | `glob` / `regex` | `glob` |
| `judge.votes` | `1` / `3` | `1` |
| `judge.aggregation` | `majority` | `majority` |
| `judge.early_stop_on_agreement` | bool | `true` |

`hardcheck_only` evaluates no description items; it approves on deterministic checks and emits `review.warn` saying N description items were not evaluated. `judge_only` is the old behaviour kept for comparison/debugging — it deliberately re-exposes the K1 conflict and should not be used in production.

## Compatibility

- No wire message, provider, storage, tool, or IPC frame changed.
- `review.hardcheck` and `review.judge` are plugin-internal; their inputs changed but the engine owns both sides.
- `review.warn` text changed for `min_points` soft items (`按软判据接受…`) and for missing description items (`… 条描述型判据未评估`). The event code and fields are unchanged.
- Default `auto` is a behaviour change: rubrics with only hard criteria no longer call the judge; rubrics with a description item call it once. This is intentional and is the point of K1.
- Bench JSON adds `boot_ms_p90`, `boot_sample_count`, and `env.reliability` / `env.note`; consumers that ignore unknown fields are unaffected.

# FeatherAgent v1.2.1-rc.4 — Changes

Release candidate, 2026-11-25. This candidate fixes the five findings from the rc.3.6 Windows retest (N5–N9) and implements the requested search-result persistence and file-attachment paths. It does not replace a stable release.

## N5 — `must_include` match modes

A multi-item `must_include` no longer defaults to “all terms must appear”. Each item is normalized at guide time with:

- `match: "any" | "all" | "min"`;
- `min_matches: 1..n` when `match` is `min`;
- default for `n > 1`: `min` with `ceil(n/2)`;
- a single item is equivalent to `all`.

Hardcheck counts the number of satisfied `must_include` items (each item still splits into word terms via `include_terms`) and compares that count with the required number. The failure message reports `{hits}/{total}`, the criterion, the mode, and the required count, without echoing the literal phrase.

Validation rejects an unknown `match`, an out-of-range `min_matches`, and `match` on an item with no `must_include`.

Tests: `review_rubric_defaults_multi_must_include_to_half`, `review_hardcheck_supports_any_all_and_min`; the existing TCP test now uses explicit `match:"all"`.

## N6 — subjective criteria cannot use `must_not_include`

The parser recognizes subjective words including `准确`, `准确无误`, `正确`, `恰当`, `专业`, `规范`, `流畅`, `自然`, and the earlier readability words. If a criterion/check is subjective and the item has `must_not_include`, guide validation fails with a message that asks for a countable/checkable form or for the judge to handle it. A banned word that already appears in the user input also rejects the guide, because the rubric contradicts the task.

`GUIDE_SYSTEM` states the `match`/`min_matches` rule and the subjective-ban rule in items 4 and 9. N4’s fixture-item drop remains covered by the rc.3.5 raw regression test.

Tests: `review_rubric_rejects_subjective_must_not_include`, `review_rubric_rejects_banned_word_from_input`.

## N7 — unique bench temp directory and structured errors

Bench previously used a temp directory keyed only by PID; Windows PID reuse could collide with a stale directory and surface `os error 2`. Every run now creates `fa-bench-<pid>-<random_token(6)>`, and no “delete the old pid directory” step remains.

The CLI is split into `bench` (argument/JSON wrapper) and `bench_run`. On failure, `bench --json` prints one JSON line before the normal error:

```json
{"ok":false,"code":"artifact_missing","error":"...","hint":"..."}
```

`os error 2` maps to `artifact_missing`; other failures use `bench_failed`. Key paths add `[bench:temp_dir]`, `[bench:kernel_init]`, `[bench:boot_ready]`, `[bench:log_store]`, `[bench:rpc_kernel]`, `[bench:rpc_ready]`, `[bench:rpc_connect]` and include the path. Both `kernel.rs` and `kernel_en.rs` carry the same logic.

## N8 — duplicate tool-call suppression

Within one model reply, `tool_calls` with the same `name` and same serialized `arguments` are executed once. Calls with different arguments still execute separately. `tool.call` now carries:

- `attempt`: 1-based model attempt in the `run_turn` retry loop;
- `call_index`: position within that reply.

This distinguishes “the retry produced the same call again” from “one reply asked for several calls”.

## N9 — reliability-aware boot gate

Bench reads `reliability` from `env_fingerprint`; only `high` is trusted. The raw gate remains `boot_p50 < boot_limit`, while the effective gate is `raw || !trusted`. The boot gate is no longer red solely because a host under memory pressure has a noisy warm start.

New fields:

- gates: `boot_gate_status` (`pass` / `fail` / `advisory`), `boot_gate_trusted`, `boot_gate_raw`, `reliability`;
- metrics: `reliability`, `boot_gate_raw`, `boot_gate_trusted`.

`boot_lt_20ms` / `boot_lt_100ms` use the effective value. `kernel.rs` and `kernel_en.rs` are synchronized.

## Search-result persistence

`web.search`, `web.news`, and `web.fetch` results are written as pretty JSON to:

```text
workspace/<project>/.featheagent/search/<unix_ms>-<random_token(4)>-<tool>.json
```

The file contains `tool`, `arguments`, `result`, `untrusted:true`, and `saved_at_unix_ms`. The tool result gains `artifact` (actual path) and `artifact_kind`. A write failure does not fail the search; it appends `persist_error`.

`save_web_artifact` is shared by the runtime path and the integration test `web_search_artifact_is_persisted_under_project_workspace`.

## File attachments

Kernel:

- `file.attach` / `file.prepare` accept either `path` (local file) or `name` + `data_base64` (browser upload).
- A local path is canonicalized and must be a file. If it is inside the canonicalized install root, it is returned unchanged (`copied:false`); otherwise it is copied to `workspace/default/uploads/<unix_ms>-<random_token(4)>-<safe_name>`.
- Browser bytes always land in the default workspace; empty files and files over 8 MiB are rejected.
- The result is `{path, copied, source, name, bytes}`; the model only receives the returned path.

TUI:

- `@<path>` at the start of a line or after whitespace; `@"path with spaces"` is supported; e-mail addresses do not trigger.
- The TUI checks `is_file` before `chat.send`, calls `file.prepare`, and appends `[附件] <kernel path>` (English: `[Attachment] <path>`) to the outgoing text. A missing file stops the send and reports it in the status line.
- `/help` lists `@<path> attaches a file` / `@<路径> 添加附件`.

WebUI:

- `+` button opens the native picker via a hidden `<input type="file" multiple>`.
- Files are read as base64 and uploaded through HTTP RPC `file.attach` (not WebSocket, whose frame limit remains 1 MiB). The HTTP body limit is 12 MiB, leaving room for an 8 MiB file encoded as base64.
- Chips show the kernel path and can be removed; upload state disables sending; switching sessions clears attachments.
- Sent text includes the same `[附件]` / `[Attachment]` line.

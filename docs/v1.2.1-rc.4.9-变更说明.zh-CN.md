# FeatherAgent v1.2.1-rc.4.9 变更说明

> 基线：`v1.2.1-rc.4.8`（提交 `a192ad3`）
> 依据：《Windows 真机复测报告 v1.2.1-rc.4.8》，问题 N43–N46
> 日期：2026-11-27

## 摘要

rc.4.8 的真机复测确认三项主要目标已经达成：N42 强杀后 5/5 干净，N40 的 ML02 公式变体 3/3，N41 的 ML10 四步拆分稳定命中；N36 的 9 字中文 evidence 也在第 1 次运行中被接受。第 2 次写文件任务失败的原因不是门限，而是 judge 返回了空 evidence。

本轮处理报告新增的三条：

- **N43（🟠）**：空 evidence 被并进“evidence 过短”，连续两次后整轮 `degraded`。空串应视为该票无效并重试，与“过短”分开处理。
- **N44（🔴）**：正文已经生成，收尾的畸形 XML 工具标记让 provider 报错，整轮被置 `failed`。已有正文必须保留，尾部畸形标记降级为 `review.warn`。
- **N45（🟠）**：模型先算出正确结果，再声称“用 Python 验证”，但没有真正调用工具，随后凭想象否定已有推导并草草收尾。系统提示需要明确“要么调用工具并等待结果，要么相信已有推导”。

**N46（🟡）** 是观察项：同题长度 140–3514 字。本版在数学/推导提示中加入“完整推导、不要重复验算凑篇幅、不要在结论前停下”，但不新增硬长度门禁，避免误杀本来正确的短答案。

## N43：空 evidence 是无效票，不是判据不合格

**现象。** 写文件任务第 2 次运行报 `审批项 c3 的 evidence 过短（须至少 6 个汉字或 3 个英文词）：""`。引号内是空字符串，说明 judge 什么都没写；旧实现把空串和短句归入同一条错误，连续 2 次后 `review.finished(status=degraded)`。

**根因。** `src/review.rs` 的 `parse_verdict` 先做 `evidence_is_substantive` 判断，空串和“总结”这类占位短句走同一个分支；`src/engine/mod.rs` 的 judge 投票循环固定每票 2 次 attempt，第二次仍空就返回 `judge 第 N 票连续 2 次未产出合规审批`。

**修法。**

- `parse_verdict` 先判断空串，返回独立错误：`evidence 为空：该票无效，必须重试并逐字复制答案原文，不是判据不合格`；顶层总结 evidence 同样处理。
- 新增 `review::verdict_error_is_empty_evidence`，引擎只在空 evidence 时把该票预算从 2 次提高到 3 次；“过短/不是原文”仍是 2 次。
- 回注给 judge 的 `[审批结果不合格]` 消息在空 evidence 场景明确说明“这是无效票，不是判据不合格”，要求从待审答案原样复制非空连续原文。
- `review.warn` 的 `retry` 字段按实际预算输出；重试用尽后错误文案带实际次数。

**验证。** 新增 `verdict_empty_evidence_is_invalid_vote_not_short_evidence`、`verdict_short_evidence_stays_a_normal_failure`、`verdict_empty_summary_is_invalid_vote`；新增集成测试 `review_gate_empty_evidence_retries_and_approves`：mock judge 第一次返回空 evidence，内核重试后 `review.finished=approved`、`chat.finished.status=ok`，且 warn 文本含“evidence 为空”而不含“evidence 过短”。

**边界。** 空 evidence 连续 3 次仍拿不到合规票时，该票仍会失败并降级；这是“judge 无法给出证据”的真实失败，不再伪装成通过。

## N44：正文已生成时，尾部畸形 XML 只降级为 warn

**现象。** ML02 内容 727 字、得分 3/3，但收尾报 `error: XML syntax error on line 4`，整轮 `status=failed`。

**根因。** `src/bin/plugin.rs` 在 provider 返回 error 时，只有累计文本能解析成工具调用才恢复；解析失败就无条件发 `error` 事件。引擎收到 error 后立刻返回 Err，已生成的正文因此被丢弃。

**修法。**
- provider 的流式 error 与 HTTP 错误体两条路径都改为：正文非空且无法恢复调用时，记录 `upstream_warn`，继续发 `done`，不再发 `error`。
- `done` 事件带完整正文 `text` 与可选 `warn`；引擎用 `done.text` 覆盖累计文本，并发出 `review.warn`（`source=provider`、`kind=malformed_tool_markup`）。
- 新增 `context::parse::strip_malformed_tool_markup`：仅在已报告 XML/工具格式错误时，截掉正文后的 `<function` / `<parameter` / `<tool_call` 等畸形标记；正常答案中的示例文本不会被调用。
- 若截掉后没有正文也没有结构化调用，仍报错；不会把纯畸形标记当成功。

**验证。** 新增 `malformed_xml_tail_is_stripped_after_content_is_kept`；新增集成测试 `provider_malformed_xml_tail_keeps_answer_and_warns`：mock Ollama 先流式返回 727 字正文，再返回 XML syntax error。最终 `model.message` 保留“巴塞尔问题”正文、不含 `<function`，事件含 `review.warn`，`chat.finished.status=ok`。

**边界。** 这是“已有正文”的降级恢复；如果模型只输出了畸形调用、没有可保留正文，仍按失败处理。Wine/Linux mock 只能证明协议路径，真实 Ollama 的 XML 变体仍需 Windows 真机复测。


## N45：验证或相信已有推导，二者只能选一

**现象。** ML10 先给出 `\frac{\pi}{16}`，随后写“让我用 Python 验证一下”，但没有真正调用工具；接着用 Beta 函数自我否定，最后以“抱歉，这个推导太复杂了”收尾。

**根因。** 系统提示只要求“写出可复核过程”，没有规定“开始验证后必须等结果”，也没有禁止在没有工具结果时否定已有推导。4B 模型会把“我该验证一下”的犹豫写进正文，却没有发出工具调用。

**修法。** 在 `src/context/mod.rs` 的系统提示中加入：
- 已有推导且有把握时，直接给出并守住结论；
- 需要验证时可以调用工具，但一旦调用就必须等工具结果再下结论；
- 不能在没有工具结果时凭想象否定已有推导；
- 要么调用工具并等待结果，要么相信并保留已有推导。

**验证。** 扩充 `system_prompt_separates_content_output_from_file_creation`，逐条断言“一旦调用就必须等工具结果再下结论”“不能在没有工具结果时凭想象否定已有推导”“严禁先给正确结论又用未执行的验证自我推翻”。

**边界。** 这是提示词约束，不保证 4B 每次都遵守；真实收益需在 Windows 真机上用同一道 ML10 连跑 3–5 次确认。


## N46：长度方差只做提示词收敛，不设硬门限

同题 5 次长度 140 / 973 / 1136 / 1550 / 3514 字，说明停顿与反复验算都在发生。140 字可能仍是正确但简短的答案，硬加最小长度会误杀；本轮改为在数学/推导提示中要求“完整过程、推导完成后收束到最终结论、不要用大段重复验算凑篇幅、不要在结论前草率停下”。该项继续作为观察项，不作为 rc.4.9 的硬验收条件。


## 兼容性与测试

- 前端契约没有新增帧、端点、事件类型或错误码。`review.warn` 仍是既有事件；payload 只增量增加 `source` / `kind` / `model` / `retry`。


## 兼容性与测试

- provider 插件的 `done` 事件现在带完整 `text` 与可选 `warn`；这是内核与内置插件之间的流式协议字段，内核已经兼容缺省情况。


## 兼容性与测试

- `parse_verdict` 的错误文案从“evidence 过短”分成“evidence 为空”和“过短”两种；依赖旧文案的脚本需要同步。

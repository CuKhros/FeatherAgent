# FeatherAgent v1.2.1-rc.4.3 变更说明

2026-11-25 候选版。本补丁处理 rc.4.2 Windows 复测的 N19–N22，并在 `docs/model-test-reports/` 增加本地模型测试报告归档。本候选版不替代稳定版。

## N19：冷启动不再等待 IPC 重试 deadline

rc.4.2 复测记录到 `cold_spawn_ms_p50` 约 3.18 s，五次样本在 3.18–3.31 s，`cold_spawn_lt_250ms` 恒红。报告怀疑是 bench RPC 重试；实际固定等待发生在 `serve` 启动更早的位置：

- `serve` 在创建监听端之前，会调用带重试的 `ipc::connect` 判断是否已有内核；
- N16 让这个调用对 `ERROR_FILE_NOT_FOUND(2)` / `ERROR_PIPE_NOT_CONNECTED(233)` 最多等 3 秒；
- 干净安装根下没有旧内核，于是每次冷启动都先等满 3 秒，才去创建命名管道。

修法是把“单次探测”和“正常客户端连接”分开：

- 新增 `ipc::try_connect`，只做一次 OS 连接尝试，不进入重试 deadline；
- `serve` 的旧内核检查、`wait_ready`、冒烟结束探测和 `Server::stop` 都改用 `try_connect`；
- 真实客户端与 `bench` 仍用有界重试的 `connect`，N16 对 Windows 命名管道创建窗口的保护不变。

Linux release bench 的冷启动 P50 为 **5.848 / 5.376 / 5.556 ms**（三连跑；当时 load average 1.31，不是安静机器的最优值）。Windows 应回到真实进程启动成本，而不是固定 3 秒；仍需下一轮真机确认。

测试：`try_connect_does_not_enter_the_retry_deadline`。

## N20：代码答案留在答复里，不默认写文件

rc.4.2 的七题试卷暴露了“工具优先”的副作用：题目要求“实现 O(1) 的 LRU 缓存”时，模型调用 `tool.fs.write` 把代码写进文件，而不是在答复里给代码块。关键词评分仍给 5/5，但用户可见交付更差。

系统提示现在区分内容输出与文件创建：

- 用户要代码、文本、方案或译文时，默认直接在答复里给出；
- 只有用户明确要求保存、写入或创建文件时才调用文件工具；
- 工具优先只用于必须获取或变更的信息。

测试：`system_prompt_separates_content_output_from_file_creation`。

## N21：列举类第一层条目对齐用户要求的对比轴

rc.4.2 的 TCP/UDP 三区别仍漏掉“开销 / 头部大小”：第一层写成了连接建立、可靠性与顺序、错误检测与纠错。提示词现在要求：

- 先确认用户要求的数量和维度，再写列举或比较；
- 第一层条目直接对应用户要求的维度；
- 用户未指定维度时，覆盖机制、可靠性/一致性、性能与开销、适用场景；
- 不要用同一维度的近义表述占位。

测试：`system_prompt_distinguishes_brevity_from_coverage` 增加对比轴断言。

## N22：写文件类 review 校验文件内容，不校验答复措辞

rc.4.2 的写文件任务不再 `failed`，但 review-gate 仍判 `unapproved`，模型还反复 `tool.fs.read` 4 次。原因是门禁只看最终答复文本：文件写对了，答复没逐字复述内容，就会被判不合格。

review 路径现在把明确的写文件任务当作“产物任务”：

- 引擎按本轮记录最近一次成功 `tool.fs.write` 的路径与内容；
- 任务明确要求写入文件时，judge 会在最终答复前收到带标签的文件内容作为验收证据；
- guide 被告知核对写入成功、目标路径与文件内容，不得要求最终答复逐字复制文件；
- 系统提示要求文件写入成功后不要为了自检反复读取同一文件。

文件内容证据只在明确的写文件任务里追加，因此 N20 的“代码题误写文件”不会被这项改动掩盖。

测试：`review_file_evidence_is_only_for_explicit_write_tasks`、`review_answer_includes_written_file_content_before_final_answer`、`review_gate_validates_written_file_content_instead_of_answer_wording`。

## 验证

- `cargo fmt --check`：通过。
- `cargo clippy --locked --all-targets -- -D warnings`：通过。
- `cargo test --locked --all-targets`：**189 项测试，188 通过，1 ignored**（`local_web_search_tool_via_kernel`，需公网）。
  - 分项：73 lib、31 plugin ×2、2 kernel、5 TUI、4 WebUI ×2、2 golden、36 integration（1 ignored）。
- Release bench（Linux VM，连续 3 次）：内核 **2,564,584 B（2.45 MiB）**；热启动 P50 **1.220 / 1.339 / 1.231 ms**，P90 **1.597 / 1.353 / 1.557 ms**；冷启动 P50 **5.848 / 5.376 / 5.556 ms**；空闲 RSS **1,920 / 1,920 / 1,792 KiB**；写入 P95 **8.924 / 8.796 / 7.704 µs**；组装 P95 **0.177 / 0.124 / 0.120 ms**；RPC P95 **0.048 / 0.071 / 0.042 ms**。发布门禁全绿；`advisory_gates.boot_gate_trusted=true`、`reliability:"high"`。
- Linux `serve + chat` 打包冒烟：见发布核对记录。Wine 冒烟：`version` 可启动，连续 5 次 `bench --json` 均完成，无 RPC 连接失败；冷启动 **442–507 ms**，仍超过 250 ms 门限（Wine 进程启动开销），因此 Wine 下 `cold_spawn_lt_250ms` 为红。Wine 只作启动冒烟，不是 Windows 结论。

# FeatherAgent v1.2.1-rc.3.5 changes

This candidate fixes M1 and M3 from the rc.3.4 real-hardware retest and strengthens the S3 tool-call prompt (M4). The rc.3.4 retest met all three checklist items: criteria became task-specific (4 of 5 tasks had real criteria, 2 approved), artifacts matched the reported paths, and feedback no longer leaked a literal phrase. The remaining failures were rubric-quality problems, not transport or wiring problems.

Real 7B data from that retest: a1 operating-system task unapproved over 3 rounds, a2 TCP handshake **degraded** after the guide was rejected 3 times, a3 memory-leak task approved, a4 TCP handshake approved, a5 “ban the word system” task unapproved (self-contradictory, correctly rejected). Approval 2/5, degraded 1/5.

## M1 · The guide discussed the placeholder instead of the task (🟠)

**Symptom.** For a2, `c1` was normal (`must_include:["SYN","ACK"]`) and `c3` had `min_points:3`, but `c2` became a criterion *about* the placeholder: `criterion:"禁止使用示例中的占位词"`, `check:"检查答案中是否出现 <...> 占位符"`, `must_not_include:["<...>"]`. Validation correctly rejected it, yet all three retries produced the same item, so the whole round degraded.

**Fix.**

- `GUIDE_SYSTEM` example values are now `__FILL_CRITERION__`, `__FILL_CHECK__`, `__FILL_PHRASE__` and similar tokens instead of `<...>`. A model can copy the field name but not mistake an angle-bracket mock for a task phrase.
- New prompt rule 8: the example only shows field names and structure. Do not discuss placeholders, examples or templates inside a criterion, do not put `__FILL_*__` into `must_not_include`, and do not write self-referential items such as “forbid placeholders”.
- New prompt rule 9: do not write subjective criteria (concise, clear, beautiful, fluent, easy to understand, logical, well-formatted). When length or shape matters, use countable keys such as `min_points`, `pattern` or `regex`; otherwise omit the item.
- `rubric_placeholder` now also rejects `__FILL*__` and any text containing `{{` or `}}`.
- `placeholder_meta(t)` detects an item only when a concrete meta phrase (“placeholder in the example”, “example criterion”, “template marker”, `__FILL`, `<...>`) appears **together with** an action word (“forbid / must not / check / appear / use / contain / mention / fill in”). It deliberately does not match the bare word “placeholder”, so legitimate tasks such as “explain what a placeholder does” or “template method pattern” survive.
- `strip_placeholder_meta_items` parses the rubric, drops only items whose `criterion`/`check` hit placeholders or `placeholder_meta`, and keeps the rest. Empty `criterion`/`check` are not dropped: that is a structural error and must still fail parsing. If every item is placeholder/example text, parsing returns a clear error instead of producing an empty rubric.
- `parse_rubric_with_input` runs the strip before normal validation and adds `已丢弃占位符/示例判据 c2（…）` to `warn`. For the a2 sample, `c1` and `c3` survive and the round no longer degrades.
- `must_include` now accepts both a string and an array of strings. The a2 form `["SYN","ACK"]` is normalized to an array and hardcheck requires every phrase, instead of silently degrading the item to judge-only.

The report's fourth suggestion, kernel-generated skeleton forms, is still not implemented. Placeholder hardening, an explicit meta rule, meta-item stripping, array support and subjective downgrade cover the observed failure paths with less prompt rigidity.

## M3 · Subjective criteria made the judge swing (🟡)

**Symptom.** a1 `c4` said “judge whether the answer is concise and clear” with no checkable standard. The judge returned different conclusions across three rounds and dragged the whole round to unapproved.

**Fix.**

- Prompt rule 9 tells the guide not to emit such items.
- If a description-only item still hits an unambiguous subjective adjective (`简洁`, `清晰`, `美观`, `通顺`, `易懂`, `可读性`, `逻辑性`, `完整性`, `语气`, `排版`), it is marked `advisory:true` with `advisory_reason`, excluded from hardcheck and judge, and reported through `review.warn`: `验收项 cX 是主观判据（含『…』）：不计入门禁；需要时改成可计数/可核对的格式`.
- `review.parse_rubric` returns `advisory` ids alongside `judge_only`, so the kernel and artifacts show which items were advisory rather than silently ignored.
- The matcher uses specific adjectives only. It does not include `明了`, because `说明了用途` contains that substring and a real descriptive criterion was once misclassified.
- Kernel guard: if a parsed rubric has `hard_items == 0` **and** `judge_only == 0` (only subjective or empty descriptions), `review_prepare` retries with the error `整份清单没有可执行判据：只有主观评价或空描述，必须补一条可计数/可核对的判据`. After the third attempt it fails instead of accepting an uncheckable rubric. A rubric with hard items plus advisory items proceeds normally; a rubric with description items still goes to judge as before.

## M4 · S3 t6 sometimes answered without calling a tool (🟡)

`tools/s3_batch.py` now opens t6 with “必须先调用 tool.fs.read 一次 … 禁止不调用工具直接凭猜测回答”, while keeping the existing one-call limit and the ban on `tool.shell` / `tool.ping`. This is a prompt-level hardening only; the 4B model's behaviour still needs a live Ollama run.

## Compatibility and settings

- No wire message, IPC frame, provider, storage or tool contract changed.
- `review.parse_rubric` output gains `advisory`; `review.warn` gains the drop/subjective notes. Consumers that ignore unknown fields are unaffected.
- `plugins/review-gate/plugin.json` still declares 14 fields. No new switch was added.
- Rubric validation remains strict for structural errors and placeholders; it is more permissive only for array `must_include` and for dropping self-referential meta items.

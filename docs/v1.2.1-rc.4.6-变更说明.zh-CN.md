# FeatherAgent v1.2.1-rc.4.6 — 变更说明

> 基线：`v1.2.1-rc.4.5`（提交 `4dc2ded`）
> 依据：《Windows 真机复测报告 v1.2.1-rc.4.5》，问题 N32–N35
> 日期：2026-11-26

## 摘要

rc.4.6 不是只修四个报告项。先做了一次代码堆积审计，确认 rc.4.5 存在五处真实的结构性技术债：中英 Rust UI 生成链失效、review 解析层单函数带不可达分支、`bench --json` 的 `gates` 语义混放、输出上限 512 硬编码、WebUI 英文包手工维护且漏附件发送。本轮按“回到过去形态再重规划”的方式处理了这五处，同时修复 N32–N35。

## N32：judge 输出里的 Windows 反斜杠

**根因**：N29 把 `tool.fs.write` 的成功路径和文件内容交给 judge，Windows 路径里的 `C:\Users\...` 被模型原样塞进 JSON 字符串，`\U`/`\w` 成为非法转义；judge 的 3 次输出都因此解析失败，整轮 `degraded`。

**修复**：

1. 新建 `src/review.rs`，统一 review 解析层；`plugin.rs` 只保留 adapter。
2. 新增 `parse_json_value` + `repair_json_text`：先按标准 JSON 解析；失败后只在字符串内部修复非法反斜杠转义（`\P`/`\w` 等补成 `\\`）、裸换行/回车/制表符和 `<0x20` 控制字符；`\u` 校验 4 位十六进制。不做全局替换，避免破坏合法 JSON。
3. `json_slice` 同时支持顶层对象和顶层数组，并优先取更早出现的 `{`/`[`。
4. 传给 judge 的证据路径统一用正斜杠 `/`；judge system prompt 要求“引用路径一律用正斜杠，JSON 字符串里的反斜杠必须写成 `\\`”。原始路径仍保留在工具事件与最终答复里。

测试：`verdict_repairs_windows_backslash_escapes`、`rubric_repairs_windows_backslash_escapes`、`json_slice_accepts_top_level_array`。

## N33：答案被截断

**根因**：`ModelProfile.max_output` 在引擎两处硬编码 512，`Config` 没有输出上限字段，provider 请求从不传 `num_predict`/`max_tokens`。M20 的 390 个中文字约 500 token，正好撞上 512。

**修复**：

- `Config.max_output` 默认 **2048**，校验范围 128–8192，设置页可改。
- 两处 `ModelProfile` 改读 `cfg.max_output`；`run_model` 与 review 调用都把它传给 provider。
- provider：Ollama 写 `options.num_predict`，OpenAI 兼容写 `max_tokens`，temperature 保留。
- 正常对话的 `ModelMessage` 增加 `truncated`（`finish=length` 时为 true）。
- 三段校验若 `finish=length` 直接报“输出达到 max_output 上限，结果可能不完整”，触发重试；不再把半截 JSON 当有效结果。

测试：`truncated_review_output_is_an_error`；provider 集成测试断言 Ollama 请求含 `num_predict:2048`、OpenAI 兼容请求含 `max_tokens:2048`。

## N34：`gates` 混放诊断值

**根因**：`bench --json` 的 `gates` 同时放布尔判定、`platform`、`reliability`、`*_gate_status`、`*_gate_raw`、阈值和模式；按“数 False”判定的消费者把 `write_gate_raw=false` 当成失败。

**修复**：

- `gates` 只保留布尔判定项：`binary_le_8mb`、`rss_le_15mb`、`assemble_p95_lt_30ms`、`rpc_p95_lt_1ms`、`metrics_consistent`、`boot_lt_*`、`cold_spawn_lt_*`、`write_p95_lt_*`。
- 新增 `diagnostics`：`platform`、`boot_gate_raw/status/trusted`、`write_gate_raw/status`、`reliability`、`boot_mode`、`boot_limit_ms`、`cold_spawn_mode`、`cold_spawn_limit_ms`、`write_limit_us`。
- `bench --json` 顶层为 `metrics/gates/diagnostics/advisory_gates`。
- `scripts/ci.sh` 增加“gates 全为布尔”断言，并把状态/原始读数的读取位置改到 `diagnostics`。

**契约变化**：旧脚本若从 `gates` 读 `write_gate_status` / `write_gate_raw` 会失效，需改读 `diagnostics`；判定项 key 不变。

## N35：`reliability` 只看内存

**根因**：rc.4.5 的 `reliability` 只由内存占用决定；warm 115 ms 仍判 `high`，没有反映同刻的 CPU 竞争。

**修复**：

- `env_fingerprint` 增加 `cpu_load_pct`、`cpu_load_source`。
- Linux：`loadavg_1m / cpu_count * 100`，上限 100，来源标 `loadavg_1m/cpu_count`。
- Windows：`GetSystemTimes` 采样 250 ms；`kernel time` 已含 idle，按 `(kernel+user-idle)/(kernel+user)` 计算。
- 新增 `reliability_grade` 与 `merge_reliability`：内存/CPU 任一 ≥70 为 medium、≥85 为 low，取更差；两者都未知才 unknown。
- `reliability_basis` 输出 `mem=%cpu=%`；note 改为“整机内存或 CPU 占用偏高…”。

测试：`reliability_uses_worse_of_memory_and_cpu`、`env_fingerprint_reports_cpu_and_memory_basis`。

## 结构性重构

### review 解析层抽库

`src/bin/plugin.rs` 3,028 → 2,219 行（-809）；新增 `src/review.rs` 924 行，只放纯函数。`parse_rubric_with_input` 重排：循环开头统一构造 `id/criterion/check/weight` 基础 `norm`；`file_task` 只保留一个早分支；后半段只处理普通任务，删除不可达的第二个 `file_task` 分支。

### 中英生成链恢复

以 `v1.2.1-rc.3.6` 的 166/72 条映射为基线，按当前 `sorted(zh)` 顺序重建 `scripts/en-ui/tui_en.py`、`kernel_en.py`，补齐 rc.4/rc.4.5 新增翻译。`gen-en-ui.py` 只生成 `src/bin/tui_en.rs` 与 `src/bin/kernel_en.rs`，成功后 `cargo fmt --all`；生成两次哈希一致，两文件无中文残留。CI 增加“重新生成后工作树无 diff”。

### WebUI 英文包

明确 `web/app.en.js` + `web/index.en.html` 为独立维护 bundle。新增 `scripts/check-en-web.py`：英文 JS 无中文、中英函数名/元素 id/RPC 方法集合一致、英文 HTML 元素 id 与中文一致、`lang="en"` 且引用 app 脚本。补回英文附件发送、`file.attach` 60,000 ms 超时、插件清单/版本/保存插件设置三处中文残留。

### 未动的部分

`engine/mod.rs`（3,712 行）、`tui.rs`（3,222 行）、`plugin.rs`（2,219 行）仍有继续拆的空间，但没有本轮可指认的不可达分支/双实现，留到专门重构轮；详见《代码堆积审计 v1.2.1-rc.4.6》。

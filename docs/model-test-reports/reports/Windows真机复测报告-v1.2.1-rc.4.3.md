## 2. 🔴 N23（新，阻断）：bench 卡死

### 2.1 现象

```
=== rc.4.3 ===
bench[1/6] 二进制体积
bench[2/6] 热启动（同一安装根，1 次预热 + 5 次中位） / RSS

```

连续 5 次跑 `bench --json`，**全部产出 0 字节文件**，每次都要等满 200s 超时。

### 2.2 同刻对照：rc.4.2 正常

```
=== rc.4.2（同一时刻）===
bench[1/6] 二进制体积
bench[2/6] 热启动（同一安装根，1 次预热 + 5 次中位） / RSS
bench[3/6] spawn serve / 冷启动
bench[4/6] 事件写入
bench[5/6] 上下文组装
bench[6/6] RPC 往返
FeatherAgent 内核实测（1.2.1-rc.4.2）
  环境指纹        cpu=20  load1=n/a  可用内存=7734 MiB
  二进制体积      2.20 MiB   (≤ 8 MiB)
  热启动 P50/P90   102.34 / 115.42 ms
  冷启动 spawn P50 3170.58 ms      ← rc.4.2 的 N19 现象（3.17s）
  空闲 RSS        10516 KiB
```

**rc.4.2 六步全过、rc.4.3 卡在第 2 步** —— 确认是这版引入。

### 2.3 与 N19 修复的关系（推断）

changelog 说 N19 的修复是：`serve` 改用 **one-shot `ipc::try_connect`**（避免等满 3 秒），
而 `wait_ready` / smoke probe / `Server::stop` 也改用它。

**推测**：bench 的第 2 步（热启动 + RSS）依赖 `wait_ready` 或 probe 判断"内核就绪"，
而 `try_connect` 是**一次性**的（不重试）——**如果内核还没起好，它就永久判定未就绪，于是死等**。

**建议**：
1. 热启动/探针路径需要"**短间隔轮询 try_connect**"，而不是"一次 try_connect 后阻塞等待"；
2. 给 bench 的每一步加**内部超时 + 明确错误**（现在是无限期静默）；
3. 加一条 CI 用例：`bench --json` 必须在 60s 内返回。

### 2.4 附带问题：临时目录堆积

```
/c/Users/[user]/AppData/Local/Temp/fa-bench-11776

每次 bench 建一个唯一目录（N7 的修复），但**卡死后不清理** → 持续堆积。建议退出时 `Drop` 清理或启动时清理超 1 天的目录。

warn:     没有描述型判据：judge 不参与本轮，全部由确定性判据决定

notes2.txt: - 引用计数是 C++/Python等语言常用的自动垃圾…
```

### 5.1 两个问题叠加

**① 仍然 `failed`（不是 `unapproved`）**

```json
chat.finished {"error":"XML syntax error on line 3: element <function> closed by </parameter>",
               "status":"failed"}
```

**N15 的 XML 恢复在 rc.4.2 上对同类任务是生效的（2/2 走完），rc.4.3 又出现 failed** —— 可能是新变体或回归。

**② rubric 本身不可满足**

`rubric-final.json` 里：

```json
{"id":"c1","criterion":"内存管理要点写入 workspace/notes2.txt",
 "must_include":["- 内存分配","- 内存回收","- 页面置换"], "match":"min","min_matches":2}
```

要求文件里出现**这三个具体词中的两个**，而模型写的是「引用计数…」，必然不匹配。

**N22 的设计意图是"让 judge 去看文件内容"，但这里 `votes=0`（judge 根本没参与）**，
因为判据全是 `must_include`（确定性类），走的是 hardcheck —— **N22 的文件证据通道对"确定性判据"不起作用**。

**建议**：
1. 写文件类任务的判据应**默认走 `description` 交由 judge 核文件内容**，或直接改为**校验文件是否存在/行数**（内核已有文件访问能力，不需要靠答案措辞）；
2. `must_include` 不应被 guide 用于"文件里必须出现某词"；
3. XML 恢复需要覆盖本次这种变体。

### 6.2 裸跑 4 题空响应的证据

```
Q4 裸跑: 66.2s len=0
Q5 裸跑: 55.9s len=0
Q6 裸跑: 53.2s len=0
Q7 裸跑: 58.2s len=0

**7 题里 4 题，裸跑跑满 50~66 秒后返回空字符串。** 这是 4B 的典型抖动（`ollama 返回空响应`）。

**FA 侧同题全部有输出** —— 靠内核的 `model.retry{reason:"empty"}` 重试救回。
**这是本轮 FA 领先的主因，也是 harness 最实在的收益。**

### 6.4 结论

> **在这套试卷上，FeatherAgent 环境再次显著优于裸跑**：22/24 vs 11/24，且快 2.7 倍。
>
> 差距主要来自 **空响应重试**（裸跑 4/7 题交白卷），其次来自 **结构化输出**（表格、术语保留、分点）。
>
> 需注意：**Q7 的失分是我打分规则的问题**（粗体 vs 列表），实际内容合格。

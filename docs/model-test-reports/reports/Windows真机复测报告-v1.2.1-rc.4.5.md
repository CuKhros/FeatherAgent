## 3. N30：写入门禁的 10–20 ms 区间 ✅

连续 3 次 bench：

| # | write P50 / P95 | `write_gate_status` | `write_gate_raw` | 有效门禁 `write_p95_lt_10ms` |
|---|---|---|---|---|
| 1 | 7,101 / **10,482 µs** | **advisory** | False | **True** |
| 2 | 7,237 / **10,807 µs** | **advisory** | False | **True** |
| 3 | 6,955 / **10,474 µs** | **advisory** | False | **True** |

**三次 P95 都落在 10.4~10.8 ms，全部按 advisory 处理、有效门禁为通过** —— N30 的意图完全达成。

完整 gates 快照（第 1 次）：

```
assemble_p95_lt_30ms = True      binary_le_8mb = True
boot_gate_raw = False            boot_gate_status = fail
boot_lt_100ms = False            boot_limit_ms = 100.0
cold_spawn_lt_250ms = True       cold_spawn_limit_ms = 250.0
metrics_consistent = True        reliability = high
rpc_p95_lt_1ms = True            rss_le_15mb = True
write_gate_raw = False           write_gate_status = advisory
write_limit_us = 10000.0         write_p95_lt_10ms = True
```

### 3.1 附带观察：`*_raw` 仍以 False 混在 `gates` 里

`boot_gate_raw=False`、`write_gate_raw=False` 都是**诊断值**，但它们是布尔型放在 `gates` 字典中。
按"数 `gates` 里 False 的个数"做判定的消费者（包括本次测试脚本）会误以为有两处失败。

**建议**：把 `*_raw` 移到 `diagnostics` 子对象，或在文档里明确"`gates` 中仅 `*_lt_*` / `*_le_*` 为判定项"。

### 3.2 同刻对照：`boot_lt_100ms=False` 是环境所致

```
rc.4.5: warm 115 / 124 / 118 ms
rc.4.4（同一时刻对照）: warm 1990 / 134 ms，cold 972 / 256 ms，writeP95 57 / 11.4 ms
```

**两个版本同时劣化**，说明是机器负载（QQ / Steam / PCL 等常驻）而非 rc.4.5 回归。
`reliability` 判为 `high` 只反映内存占用，**未反映 CPU 竞争**——这点值得后续补一个负载维度。

## 4. N29：写文件任务 ⚠️ 路由生效，但 judge 解析失败

任务：`请用工具把三条关于「内存管理」的要点写入 workspace/notes3.txt，每条一行，以「- 」开头`，连跑 3 次。

### 4.1 N29 的目标已达成

```
warn: 写文件任务：判据已转为 judge 核对文件内容与 tool.fs.write 成功记录；不按最终答复的字面措辞判定
warn: 4 条描述型判据（c1, c2, c3, c4）：由 judge 按 criterion 评估
```

**判据确实从"硬判据"转成了"judge 核对文件"**，`must_include:["-"]` 也不再触发两字符下限。✅

### 4.2 🔴 但 judge 的输出不是合法 JSON（3/3 次）

```
warn: 第 1 票第 1 次审批不合格：rpc -32000: 审批结果不是合法 JSON: invalid escape at line 22 column 43
warn: 第 1 票第 2 次审批不合格：rpc -32000: 审批结果不是合法 JSON: invalid escape at line 12 column 43
review.finished {status:"degraded", rounds:1}
```

| # | 结果 | judge 报错 | 工具调用 |
|---|---|---|---|
| 1 | degraded | `invalid escape at line 22 column 43` | `tool.fs.write` |
| 2 | degraded | `invalid escape at line 12 column 43` | `tool.fs.write` |
| 3 | degraded | `invalid escape at line 7 column 43` | `web.search`, `tool.fs.write` |

**症状高度一致**：`invalid escape` 且列号都是 **43**。

**推断**：N29 把 `tool.fs.write` 的成功记录与文件内容作为证据交给 judge，其中包含 **Windows 路径（反斜杠）**，
judge 在 JSON 字符串里原样复制 `C:\...`，`\P` / `\w` 之类成为非法转义 → JSON 解析失败 → 重试仍失败 → degraded。

> 这与 rc.4.4 的 N29 失败不同：上次是"判据规则自相矛盾"，这次是"**证据里的路径把 judge 的输出格式打坏了**"。
> 属于**修复引入的新形态**，不是同一问题复发。

### 4.3 建议

| 优先 | 措施 |
|---|---|
| **1** | judge 输出解析做**容错预处理**：把非法转义（`\` 后跟非 `"\/bfnrtu`）替换为 `\\` 后重试解析 |
| **2** | 传给 judge 的路径**先行转义**（`C:\\...`），或在 prompt 里要求"引用路径时用正斜杠" |
| **3** | 文件类任务改为**结构化证据**（`{path, line_count, first_line}`）而非让模型复述原始路径 |

| 试卷 | 领域侧重 | 裸跑 | FA | 分差 | 裸跑空响应 |
|---|---|---|---|---|---|
| large-1 | 八领域通用 | 30.0/54（55.6%） | 50.5/54（93.5%） | **+38.0 pp** | **8 题**（40%） |
| large-2 | 工程深水 | 45.0/60（75.0%） | 48.0/60（80.0%） | **+5.0 pp** | 3 题（15%） |

**分差从 38 个百分点缩到 5 个百分点**，关键变量不是"题目难度"，而是**裸跑的空响应率**：

- large-1：裸跑 8/20 题交白卷 → 直接丢 24 分
- large-2：裸跑只有 3/20 题交白卷 → 只丢 10 分

**结论修正**：FeatherAgent 的优势主要体现在 **"避免空响应"** 上，而**在内容质量上两边接近**
（large-2 中 FA 甚至因为"答案被截断"丢了 3 分给裸跑）。

### 6.5 耗时数据（受负载影响，仅供参考）

- 裸跑 1,059s vs FA 1,653s —— **本轮 FA 反而更慢**，与 large-1（FA 319s vs 裸跑 856s）相反。
- 原因判断：本轮后半段机器负载显著升高（见 §1），单题耗时从 60s 涨到 90~180s，且 FA 的答案普遍更长。
- **不做版本间或环境间的绝对比较**，仅记录现象。

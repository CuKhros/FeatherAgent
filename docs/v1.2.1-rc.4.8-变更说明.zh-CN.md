# FeatherAgent v1.2.1-rc.4.8 变更说明

> 基线：`v1.2.1-rc.4.7`（提交 `0c51399`）
> 依据：《Windows 真机复测报告 v1.2.1-rc.4.7》，问题 N40–N42；N36 仍待干净环境复核
> 日期：2026-11-27

## 摘要

rc.4.7 真机复测确认了两项实际收益：放行 `tool.shell` 后数学小卷 19.5→21.5、大卷 40.7→41.6，FA 耗时降到 126s / 446s；N38 的“只写标题就停”也从 MS2 37 字、ML02 109 字恢复到 729 / 1568 字。N36 因残留 turn 连续返回 `interrupted/stopped`，没有取得有效读数。

本轮处理报告新增的三条：

- **N40（🟠）**：公式类判据仍是字符串匹配，`\dfrac{\pi^2}{6}`、`\zeta(2)`、Unicode `π²/6`、`(π^2)/6` 等等价写法会漏判。
- **N41（🟡）**：部分分切分过粗，ML10 有完整推导仍只拿 1.3/4。
- **N42（🟡）**：长任务被强杀后残留 turn，同会话后续客户端会收到旧回合的 `interrupted/stopped`。

## N40：扩展公式判据

**现象。** `math-large` 的 ML02 只覆盖 `π²/6`、`pi^2/6`、`\frac{\pi^2}{6}`。报告中的 1568 字答案仍只命中 1/3，判 1.0 分；报告推断公式写成了 `\dfrac{\pi^2}{6}` 或 `\zeta(2)`。

**修法。** ML02 的公式判据扩展为：

- Unicode 上标：`π²/6`；
- ASCII/LaTeX：`π^2/6`、`π^{2}/6`、`pi^2/6`；
- 带括号：`(π^2)/6`、`(π²)/6`；
- 分式：`\frac{\pi^2}{6}`、`\dfrac{\pi^2}{6}`、`\frac{\pi^{2}}{6}`；
- 反写：`\frac{1}{6}\pi^2`；
- Zeta：`\zeta(2)`、`ζ(2)`。

ML10 的 `π/16` 同样接受 `\frac{\pi}{16}`、`\dfrac{\pi}{16}`、`\frac{1}{16}\pi`、`pi/16`。

**验证。** 新增 `math_paper_formula_variants_and_steps_are_scored`，逐项断言上述写法命中，且 `π^2/5` 不误命中。

**边界。** 本轮仍是字符串/正则覆盖，不做符号解析或数值等价比较。报告建议的“解析表达式后比较”留作后续；未知但等价的写法仍可能漏判。

## N41：ML10 按步骤计分

**现象。** ML10 满分 4，但只有 3 条判据；完整三角代换推导只命中 1 条时得 4/3≈1.3 分，无法反映“换元、展开、降幂、结果”四个步骤。

**修法。** 改为四条判据，各占 1 分：

1. 换元方法：`sin` / 三角代换 / `trig` / Beta / B 函数；
2. 换元展开：`cos` / 换元 / Beta / B 函数；
3. 降幂或倍角：`sin^2` / `sin²` / 倍角 / 降幂 / `1/4` / `1/8` / Beta；
4. 结果：`π/16` 及其等价写法。

三角代换与 Beta 函数两条路线都能拿到对应步骤分。该测试与 N40 的回归测试合并。

## N42：旧回合不再污染新连接

**现象。** 用 240s 超时强杀 chat 客户端后，同会话后续请求可能直接收到：

```
model.message {"finish":"interrupted"}
chat.finished {"status":"stopped"}
```

**复现。** 用 rc.4.7 的 Linux 发布包启动 mock provider，连续 5 次“SPIN 长回合 → 3s 强杀 → 同会话发 `echo: clean`”：第 5 次新客户端收到旧回合的 `chat.finished(status=stopped)` 并以 `exit=1` 退出，命中报告现象。

**根因链。**

- `cancel_connection` 只置 `cancel=true`、取消 provider、发 `tool.cancelled(client.disconnect)`，不递增 run 代次，也不立即把会话状态改为 `Cancelled`；
- `session.create` 可以无条件把 holder 抢到新连接，旧 turn 仍可能继续并广播自己的 `chat.finished`；
- `chat` CLI 订阅全部事件，收到任意 `chat.finished` 就当作自己的回合结束，没有按 `session` 或 `run` 过滤。

**修法。**

- `Session` 新增 `run_id: AtomicU64`；`chat.send` 调用 `begin_run()` 分配新 id，并在返回值中带 `run`。
- `run_turn` 接收 `run_id`；在回合开始、每轮开始、模型返回后、每次工具调用前、最终状态落盘前检查 `run_is_current`。旧回合直接静默退出，不写状态、不发 `chat.finished`。`run_model` 的流式循环也按 `run_id` 检查，旧回合被取代后停止拉流，避免继续广播 delta。
- 正常 `chat.finished` 增加 `"run": run_id`；失败分支同样带 `run`，且只在 run 仍当前时写 `Failed`。
- 客户端断开且会话正在跑时，`cancel_connection` 先递增 `run_id` 让旧回合失效，再取消 provider，并立即把状态置为 `Cancelled`。
- `session.create` 发现 holder 属于其他连接时，先调用 `cancel_connection` 清理旧 holder，再接管。
- `chat` CLI 保存 `chat.send` 返回的 `run`，只接受 `payload.run` 相同的 `chat.finished`；旧回合的 finish 打印一行提示后忽略。

**验证。**

- 新增集成测试 `killed_client_does_not_leak_or_block_next_run`：长回合中 drop 客户端，100ms 后新连接复用同一 session；只接受新 run 的 `chat.finished(ok)`，且正文包含 `echo: clean`。
- rc.4.8 Linux 发布包重复同一组 5 次强杀/重连，5/5 新客户端均 `exit=0`、`status=ok`、只收到 1 个 `chat.finished`（各自 run=3）。
- Wine 6.0.3 冒烟同样跑一次 SPIN 强杀后重连，新客户端 `status=ok`，`chat.finished` 带 `run=3`。

## 兼容性

- 没有新增帧、端点、事件类型或错误码。
- `chat.send` 返回值新增 `run`（u64）；`chat.finished.payload` 新增 `run`（u64）。都是增量字段，旧客户端可忽略；不按 run 过滤的旧客户端仍可能看到旧回合事件。
- `session.create` 对同会话旧 holder 的清理是行为修正：旧客户端被强杀后，新连接可以立即接管。
- N40/N41 只改公开试卷 JSON 与评分说明，不改产品协议。

## 未验证

- N36 的中文 evidence 门限仍需干净环境、真实 7B judge 复测；本轮未把它当作已修复。
- N40 没有拿到报告里 ML02 的实际答案正文，只能按报告推断补齐变体；真实答案能否到 2/3 或 3/3 需重新跑卷。
- N41 的四步判据是否与真实 4B 推导匹配，需真机重跑 ML10；本轮只验证规则本身。
- N42 的 Windows 真机强杀时序（任务管理器结束进程、命名管道清理）仍需复测；Linux/Wine 证据不能替代 Windows 结论。
- 数值等价评分、其余公式变体、TUI 手感、高 DPI、代理、网络盘/24h、macOS/arm64 未覆盖。
